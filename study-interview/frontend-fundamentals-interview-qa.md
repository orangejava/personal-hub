## 0. 如何使用

每题先用“回答”练 30 秒；“追问展开”用于解释机制和边界，不必整段背诵。源码题里的代码是**教学模型**，不是 React 或 Vue 的源码原文；手写时要说清复杂度、异常和测试输入。

阅读导航：请求取消的浏览器语义看 §2.12，React 竞态处理看 §5.3；React Hook 的可运行模型在 §8 和 `examples/`。同一知识点在通用题和源码题里出现时，先答应用场景，再展开内部机制。

## 1. JavaScript 高频题

### 1.1 `var`、`let`、`const` 有什么区别？

**回答：**“var 和 let、const 最大的区别是作用域。var 按函数划分，let 和 const 按代码块划分；const 不能重新赋值，但对象里面的属性还是能改。我平时默认用 const，需要改变量绑定时才用 let。”

**追问展开：** `var` 是函数作用域，声明会提升且初始值为 `undefined`；`let`、`const` 是块级作用域，声明提升后到初始化前处于暂时性死区。`const` 禁止重新赋值，但不冻结对象内部属性。循环闭包常用 `let`，因为每轮迭代有独立绑定。

### 1.2 什么是闭包？会造成内存泄漏吗？

**回答：**“闭包就是一个函数在外层函数结束后，仍然能用到当时的变量。比如事件回调会记住创建它时的状态。闭包本身不会泄漏；真正的问题是监听器或定时器一直没清理，导致那批变量一直被引用。”

**追问展开：** 闭包常用来封装私有状态，比如工厂函数返回一个计数器。排查泄漏时要找“谁还持有这个函数”，再沿引用链看它是否保留了不再需要的大对象。

### 1.3 `this` 到底由什么决定？箭头函数有什么不同？

**回答：**“普通函数的 this 看它怎么被调用，obj.fn() 里的 this 通常就是 obj；箭头函数则从定义位置取 this。我遇到回调丢 this 时，会先看它是不是被当成独立函数传出去了。”

**追问展开：** 普通函数的 `this` 主要由调用方式决定：`obj.fn()` 指向 `obj`，`call/apply/bind` 可以显式指定，`new` 创建实例绑定；独立调用在严格模式下是 `undefined`。箭头函数没有自己的 `this`，从定义位置的外层词法环境取得，因此不能作为构造函数。

### 1.4 原型链和 `class` 是什么关系？

**回答：**“JavaScript 对象找不到自己的属性时，会沿原型链继续找。class 让写法更像传统面向对象，但实例方法和继承底下仍靠原型机制。”

**追问展开：** 对象通过内部 `[[Prototype]]` 连接到原型对象，属性查找会沿链向上。`class` 是更清晰的定义语法，实例方法通常放在 `prototype` 上，继承仍建立在原型机制之上。`Object.getPrototypeOf(obj)` 查看实际原型，不能把 `__proto__` 当成推荐的业务 API。

### 1.5 `==`、`===` 和 `Object.is` 怎么选？

**回答：**“日常我优先用严格相等，因为它不会做隐式类型转换。Object.is 在比较 NaN 和正负零时更精确；比如 React 比较依赖时会用它。两个对象是不是相等，仍然看是不是同一个引用。”

**追问展开：** `===` 不做类型转换，日常比较优先用它；`==` 会触发抽象相等转换，容易出现 `'' == 0` 之类的意外；`Object.is` 与 `===` 的主要差异是它认为 `NaN` 等于自身，并区分 `+0` 与 `-0`。比较对象时三者都关注引用身份，不做深比较。

### 1.6 事件循环如何决定输出顺序？

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
// A D C B
```

**回答：**“这段代码先输出同步的 A、D，再执行 Promise 的微任务 C，最后才轮到定时器 B，所以结果是 A、D、C、B。我一般先找同步代码，再看微任务，最后看下一轮任务。”

**追问展开：** 当前同步代码先运行；当前任务结束后，环境清空微任务队列，随后处理下一个任务。Promise 回调是微任务，计时器回调是任务。浏览器的渲染时机由用户代理安排，不能简单说“每个宏任务后一定渲染”。

### 1.7 `async/await` 和 Promise 的关系是什么？

**回答：**“async 函数返回 Promise，await 只是让当前函数后面的代码等结果，不会卡住整个浏览器。如果几个请求互不依赖，我会先同时发出，再一起等待，避免无意中串行。”

**追问展开：** `async` 函数总返回 Promise；`await` 等待表达式的完成值，并让后续代码在异步恢复时运行。`await` 不是阻塞整个 JavaScript 线程。错误可用 `try/catch` 捕获；若多个独立请求要并发，应先启动它们再 `Promise.all`，不要无意中串行 `await`。

### 1.8 `Promise.all`、`allSettled`、`race`、`any` 怎么选？

**回答：**“我按需求选：都成功才继续用 all；想拿到每个任务的成败用 allSettled；只关心最先结束用 race；只要一个成功用 any。它们都不会自动取消其他任务。”

**追问展开：** `all` 要全部成功，任一拒绝就拒绝；`allSettled` 等待全部结果并保留成功/失败状态；`race` 取第一个落定结果；`any` 取第一个成功结果，全部失败才拒绝。它们都不自动取消仍在运行的其他任务，取消需要 `AbortController` 等配合。

### 1.9 防抖和节流的区别？

**回答：**“搜索输入我常用防抖，停下来一会儿再发请求；滚动反馈更适合节流，限制更新频率。两者都要处理组件卸载时的取消，否则旧回调可能继续执行。”

**追问展开：** 防抖在持续触发结束后一段时间才执行，适合搜索输入；节流限制一段时间内的执行频率，适合滚动或拖拽反馈。两者都要考虑首尾调用、取消和组件卸载。动画相关更新也可用 `requestAnimationFrame` 与浏览器帧同步。

### 1.10 浅拷贝、深拷贝与 `structuredClone`？

**回答：**“展开对象只是浅拷贝，里面的嵌套对象仍然共用。确实需要完整复制时可以考虑 structuredClone，但它也不是万能的，比如函数不能复制。更新 React 状态时，我通常只复制改动的那条路径。”

**追问展开：** 展开语法只复制一层引用；嵌套对象仍共享。`structuredClone` 能处理很多内建数据类型和循环引用，但不能克隆函数、DOM 节点等，也不保留所有自定义对象语义。业务上优先只复制需要更新的路径，避免为一次状态更新深拷贝整棵树。

### 1.11 如何理解垃圾回收与常见泄漏？

**回答：**“我判断内存泄漏会看对象为什么一直可达。常见原因是忘记清理监听、定时器、订阅，或者缓存无限增长。排查时用堆快照看引用链，比只盯内存曲线可靠。”

**追问展开：** 主流引擎通过可达性判断对象是否可回收。长期存活的事件监听、定时器、未清理的订阅、无界缓存和保留 DOM 引用都可能让对象保持可达。排查时用堆快照比较保留路径，而不只是看内存曲线是否短期上升。

### 1.12 CommonJS 与 ESM 有什么区别？

**回答：**“ESM 的 import/export 在编译阶段就能看出依赖，更方便做 Tree Shaking；CommonJS 的 require 在运行时执行。我会特别留意两者混用时的默认导入和循环依赖。”

**追问展开：** ESM 导入的是动态只读绑定，导出值变化后消费者能看到新值；CommonJS 消费的是 `require` 返回的导出对象。两种模块系统混用时，默认导入和循环依赖行为值得实际运行验证。

### 1.13 手写并发限制器时要注意什么？

**回答：**“并发限制器的核心是同一时间只跑固定数量的任务。一个任务结束或者失败，都要腾出位置给下一个；结果要按输入顺序返回。我会先说清失败时是继续跑还是立即停止，再写代码。”

**追问展开：** [教学实现](./examples/interview-models.mjs)启动固定数量的 worker，每个 worker 依次领取下一个任务；任务失败被记录为 `rejected`，该 worker 继续领取，不会卡住队列。结果按输入索引保存。它选择了 `allSettled` 语义，不包含取消或优先级；传入已经启动的 Promise，也无法再限制其启动并发。

### 1.14 `Map`、`Set` 与普通对象怎么选？

**回答：**“固定字段的数据记录用普通对象；需要任意类型的键和频繁增删时用 Map；只想去重或判断成员是否存在时用 Set。Map 的对象键按引用区分，内容相同不代表同一个键。”

**追问展开：** `Map` 适合任意类型 key、频繁增删和明确迭代顺序；`Set` 适合去重和成员判断；普通对象适合固定字段的记录结构。对象键主要是字符串或 Symbol，且会受原型、属性特性影响；不能把 `Map` 的键引用误认为结构相等。

### 1.15 为什么浮点数计算会有误差？

**回答：**“JavaScript 的小数是二进制浮点数，很多十进制小数存不准，所以 0.1 加 0.2 不会精确等于 0.3。金额我会用最小单位整数或 decimal 类型，测量值则按业务容差比较。”

**追问展开：** 底层 `Number` 是 IEEE 754 双精度。金额用分这类最小单位时，还要留意整数安全范围；测量值可以按业务精度设置容差，不能给所有数统一套一个 epsilon。

## 2. 浏览器与网络高频题

### 2.1 输入 URL 到页面显示，经历了什么？

**回答：**“输入 URL 后，浏览器先找目标服务器，建立连接并请求页面；拿到 HTML 后解析 DOM 和样式，再布局、绘制，最后显示出来。缓存、脚本和重定向会让实际顺序更复杂，但主链路是这样。”

**追问展开：** 浏览器解析 URL、查缓存与 DNS、建立连接并协商 TLS、发送 HTTP 请求、处理重定向和响应。HTML 解析生成 DOM，CSS 生成 CSSOM，浏览器计算样式与布局、绘制并合成图层；脚本可能改变这些阶段。现代浏览器还有进程隔离、预加载和缓存优化，面试时按主链路说明即可。

### 2.2 重排、重绘和合成有什么区别？

**回答：**“改元素大小或位置通常要重新布局；只改颜色一般重新绘制；transform 和 opacity 动画有机会主要走合成。我优化时最先避免一边读布局、一边反复改样式，因为这会强迫浏览器同步计算。”

**追问展开：** 不是所有 `transform` 动画都“零成本”，图层、绘制面积和设备也会影响结果。排查时在 Performance 面板里看 Layout、Paint 和长任务；若代码交替读取尺寸和修改样式，要先改读写顺序。

### 2.3 强缓存和协商缓存如何工作？

**回答：**“强缓存还在有效期内，浏览器可以直接用本地资源；过期后再带 ETag 等信息问服务器，没变就返回 304。带内容哈希的静态文件适合长缓存，HTML 入口则要更容易拿到新版本。”

**追问展开：** `Cache-Control` 控制有效期；协商时 `ETag/If-None-Match` 比修改时间更能表达内容是否相同。上线后若 HTML 长期缓存，用户可能继续引用已经删掉的旧 chunk，所以入口和带哈希静态资源的策略要分开。

### 2.4 Cookie、localStorage、sessionStorage、IndexedDB 怎么选？

**回答：**“我按用途选：Cookie 用于需要随请求发送的会话信息；localStorage 放少量本地偏好；sessionStorage 适合当前标签页临时数据；较大且结构化的离线数据用 IndexedDB。Token 放哪儿还要一起考虑 XSS 和 CSRF。”

**追问展开：** `HttpOnly` 让脚本读不到 Cookie，`Secure` 限制 HTTPS 传输，`SameSite` 限制跨站发送。`sessionStorage` 按标签页会话隔离；IndexedDB 能做结构化查询，但仍要设计版本升级和清理策略。

### 2.5 什么是同源策略、CORS 和预检？

**回答：**“同源指协议、域名和端口都相同。跨源时，浏览器会看服务器有没有允许这个来源；有些请求还会先发 OPTIONS 预检。CORS 只决定浏览器能不能读响应，不能代替登录和权限校验。”

**追问展开：** 同源比较协议、主机和端口。CORS 是服务器通过响应头允许浏览器脚本读取跨源响应的机制；非简单请求通常先发 OPTIONS 预检。CORS 不是服务端鉴权，服务器仍要验证身份和权限；带凭据请求也不能把 `Access-Control-Allow-Origin` 设成通配符。

### 2.6 CSRF 与 XSS 如何区分？

**回答：**“XSS 是攻击脚本在我的页面里运行，CSRF 是别的网站诱导浏览器带着现有 Cookie 去发请求。前者重点处理不可信内容的输出，后者重点看 Cookie 策略和请求来源；HttpOnly 只能保护 Cookie 不被脚本直接读取。”

**追问展开：** XSS 是不可信脚本在页面上下文执行，可读取可访问的数据并代表用户操作；CSRF 是诱导浏览器带现有凭据向目标站发请求。XSS 主要靠输出编码、可信内容净化和 CSP 等降低风险；CSRF 常用 SameSite、Origin 校验或 CSRF Token。HttpOnly 可以阻止脚本直接读取 Cookie，但不能单独解决两类问题。

### 2.7 HTTP/1.1、HTTP/2、HTTP/3 的关键差异？

**回答：**“HTTP/2 能在一条连接上复用多个请求，但 TCP 丢包仍可能拖慢整条连接；HTTP/3 基于 QUIC，改善了这类传输层阻塞。实际快多少还得看网络和资源配置，不能只看协议版本。”

**追问展开：** 如果面试官继续问“HTTP/2 已经多路复用，为何还会堵”，关键是多个流共享同一个 TCP 连接，丢包时按序交付仍会影响其他流。HTTP/3 的 QUIC 把流的传输处理移到新协议层，也支持连接迁移。

### 2.8 SSE、WebSocket 与普通轮询怎么选？

**回答：**“服务器持续向浏览器推送文字，我会优先考虑 SSE；需要真正双向实时通信，再考虑 WebSocket；状态变化不频繁时轮询也够用。选 SSE 后要处理半包、断线和代理缓冲。”

**追问展开：** SSE 适合服务端向客户端单向、连续推送文本事件，基于 HTTP；WebSocket 适合真正双向、低延迟通信；轮询实现简单，适合状态变化不频繁的任务。SSE 要处理事件边界、重连和代理缓冲；使用 `fetch` 读流时需自己实现协议解析及重连策略。

### 2.9 浏览器如何实现跨标签页通信？

**回答：**“同源标签页之间，我常用 BroadcastChannel 发消息；storage 事件也能通知其他标签页。跨窗口通信可用 postMessage，但接收方一定要检查来源和消息格式。”

**追问展开：** `storage` 事件通常只通知其他同源文档，写入它的窗口不会收到自身事件。若用 `postMessage` 和其他来源通信，接收时验证 `origin` 与数据结构，发送时指定目标来源。

### 2.10 Service Worker 有什么作用和风险？

**回答：**“Service Worker 可以拦请求做离线缓存，也能支持一些后台能力。难点在更新和失效：新版本安装后不一定立刻接管旧页面，缓存策略写错还可能一直给用户旧内容。”

**追问展开：** 它可拦截受控页面的请求，实现离线缓存、后台同步等。生命周期包含安装、等待、激活，更新不能假设立即接管所有已打开页面。缓存策略若设计错误会让用户长期拿到旧 HTML 或 API 数据，因此要明确版本、失效和回退。

### 2.11 LCP、INP、CLS 分别测什么？

**回答：**“LCP 看主要内容多久出现，INP 看交互响应，CLS 看页面有没有突然跳动。我不会只拿本机一次跑分下结论，还要看真实用户、设备和页面类型。”

**追问展开：** 分析时按设备、网络、页面类型分组看分位数，别把本机开发环境的单次数据和真实用户数据混在一起。优化 LCP 要定位最大内容元素，优化 INP 要看长任务与事件处理，CLS 则要找没有预留尺寸的内容。

### 2.12 `AbortController` 取消请求后就不会有旧结果了吗？

**回答：**“调用 abort 只是通知支持取消的操作尽快停止，旧请求可能已经完成，后续回调也可能正在跑。所以我还会在结果回来时检查请求 ID 或当前参数，确认它仍然属于当前页面。”

**追问展开：** `abort()` 让支持它的操作尽快停止，但请求可能已经完成，或后续异步处理已经开始。界面仍应检查当前请求 ID、参数版本或组件生命周期，丢弃过期结果。服务端是否停止执行也要看协议和后端是否监听连接断开。

## 3. TypeScript 高频题

### 3.1 `type` 和 `interface` 怎么选？

**回答：**“描述对象接口时，type 和 interface 大部分时候都能做。我会按团队习惯选；需要联合类型或条件类型时用 type，需要给外部扩展并允许声明合并时考虑 interface。”

**追问展开：** 两者都能描述对象形状。`interface` 支持声明合并，适合可扩展的对象契约；`type` 能表示联合、交叉、元组和条件类型。团队保持一致比机械规定谁更好重要；公开库 API 需要特别考虑声明合并是否为预期行为。

### 3.2 `any`、`unknown`、`never` 有什么区别？

**回答：**“any 是跳过检查，unknown 是知道值存在但还不知道类型，never 表示这条路径不可能有值。接口返回或异常对象进来时，我优先用 unknown，再做判断和运行时校验。”

**追问展开：** `unknown` 必须先缩小类型才能访问字段；`never` 可在 `switch` 默认分支检查是否漏了联合类型成员。`any` 会沿赋值链传播，尤其不适合放在公共接口返回值上。

### 3.3 联合类型如何做穷尽检查？

```ts
type State = { kind: 'loading' } | { kind: 'done'; value: string };
function describe(state: State): string {
  switch (state.kind) {
    case 'loading': return '加载中';
    case 'done': return state.value;
    default: {
      const impossible: never = state;
      return impossible;
    }
  }
}
```

**回答：**“我会给联合类型一个明确的 type 字段，然后 switch 分支处理。最后用 never 做兜底：以后加了新类型但忘了处理，编译器就能提醒我。”

**追问展开：** 用稳定的判别字段缩小类型，`never` 能在新增分支但忘记处理时产生编译错误。运行时收到外部数据前仍需校验，TypeScript 不能阻止服务器发来未知字符串。

### 3.4 泛型解决什么问题？

**回答：**“泛型用来保留输入和输出之间的关系，比如传入什么类型就返回什么类型。只要固定几种类型时，我不会为了炫技硬加泛型；需要对象有 id，就写清这个约束。”

**追问展开：** 泛型保留输入和输出之间的类型关系，例如 `identity<T>(value: T): T`。如果函数只需一个固定联合类型，泛型反而增加复杂度。可以用约束 `T extends { id: string }` 表达所需能力，而不是把参数写成 `any`。

### 3.5 `keyof`、索引访问类型和映射类型如何配合？

**回答：**“keyof 拿到对象有哪些键，T[K] 拿到某个键对应的值类型，映射类型可以遍历这些键生成新类型。比如 Pick 就是从原对象里挑一组字段。”

**追问展开：** 现场可以写一个 `Pick`：`type MyPick<T, K extends keyof T> = { [P in K]: T[P] }`。`K` 的约束防止传入不存在的键；映射后的每个值仍沿用原字段类型。

### 3.6 条件类型和 `infer` 用来做什么？

```ts
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;
```

**回答：**“条件类型相当于在类型层做分支，infer 可以从匹配的类型里取出一部分。写这类工具类型时，我会先用小例子验证联合类型是不是按我预期分发。”

**追问展开：** 条件类型根据类型关系选择分支，`infer` 在匹配中提取局部类型。裸类型参数参与条件判断时会对联合类型分发；不希望分发可以包在元组里，例如 `[T] extends [U]`。

### 3.7 `as const`、`satisfies`、类型断言有什么区别？

**回答：**“as const 是尽量保留字面量并设为只读，satisfies 是检查结构正确又保留推断结果，as 类型断言则可能把错误盖过去。写配置表时，我通常更喜欢 satisfies。”

**追问展开：** 比如路由配置用 `satisfies Record<string, Route>`，既能检查每项满足 `Route`，又保留具体 key 供后续引用。类型断言不会验证运行时数据，外部 JSON 更不能靠 `as Route` 变安全。

### 3.8 TypeScript 为什么不能代替 DTO 校验？

**回答：**“TypeScript 只在编译时帮忙，HTTP 发来的数据运行时不会自动变安全。所以 Body、URL 参数和第三方响应仍要校验；重要规则还要靠数据库约束守住。”

**追问展开：** `JSON.parse` 后写 `as User`，只改变编译器看法，不会检查实际字段。DTO 或 schema 校验负责拒绝非法输入；数据库唯一约束负责守住并发下仍必须成立的规则。

### 3.9 协变、逆变在回调里有什么实际影响？

**回答：**“我不死记协变逆变的符号，会用回调理解：如果调用方可能传进任意动物，就不能给它一个只会处理猫的函数。参数能接收更宽的范围，替换起来才安全。”

**追问展开：** 返回值可看作协变：返回更具体的类型通常安全；函数参数位置倾向逆变：能接受更宽类型的函数更容易安全替换。面试不必死背符号，重点是能解释“把只会处理猫的回调交给可能传入任意动物的调用方”为什么不安全。

### 3.10 前后端共享类型是否意味着接口不会出错？

**回答：**“共享类型能让前后端改字段时更早发现问题，但服务端实际返回的数据仍可能不符合声明。接口契约还需要运行时校验和测试，尤其是错误、权限和日期序列化。”

**追问展开：** 共享类型能减少字段漂移，但不能保证实际 HTTP 响应符合声明，也不能证明权限、日期序列化和数据库数据正确。还需要运行时校验、契约测试、版本兼容和异常路径验证。

## 4. Vue 原理与源码题

以下问题以 Vue 3 的实现思想为主。代码是为了说明依赖收集和调度而写的简化模型。

### 4.1 Vue 3 为什么使用 `Proxy`？

**回答：**“Vue 3 用 Proxy 代理整个对象，读和写属性时都能拦截，所以新增属性、删除属性等场景更好处理。代价是代理对象和原对象不是同一个引用，也不能把所有内建对象都当普通对象代理。”

**追问展开：** `Proxy` 可以拦截属性读取、写入、删除、`in` 和键遍历，便于对对象变化做依赖追踪。Vue 2 的 `Object.defineProperty` 需要对已有属性逐一转换，对新增属性和数组索引等场景有额外限制。`Proxy` 也有代价：代理对象与原对象身份不同，且无法代理某些内建对象的内部槽位。

### 4.2 `track` 和 `trigger` 如何实现响应式？

可运行的简化实现见 [createReactivity](./examples/interview-models.mjs)，对应测试见 [effect 分支切换用例](./examples/interview-models.test.mjs)。它包含 `Proxy` 读写、依赖收集、重新执行前清理和嵌套 effect 上下文恢复。

**回答：**“我会把它理解为‘读的时候记账，写的时候通知’。effect 运行时读到某个属性，Vue 记下这个依赖；属性变了，再通知相关 effect。分支切换后还要清理旧依赖，否则会多执行。”

**追问展开：** 教学模型用 WeakMap 关联目标对象和属性，触发前复制订阅集合，避免 effect 清理并重新订阅时重复遍历。真实 Vue 还处理调度、数组和集合等更多依赖类型。

### 4.3 `ref` 和 `reactive` 的差异？

**回答：**“基本类型或需要整体替换的值我常用 ref；一组相关字段用 reactive。ref 在 JavaScript 里通常要写 value；把 reactive 的普通字段直接解构出来，会丢掉后续的响应式读取。”

**追问展开：** 模板里某些 ref 会自动解包，但 JavaScript 代码中仍需 `.value`。如果要解构 `reactive` 的字段又保留响应性，可用 `toRef/toRefs`；不要把普通解构值误当成仍在跟踪代理。

### 4.4 `computed` 为什么能缓存？

**回答：**“computed 只有依赖变化后才失效，下次读取时重新算，所以重复读取能用缓存。它适合纯计算；发请求或改外部状态不要放在 computed 里。”

**追问展开：** `computed` 内部依赖变化时先把结果标记为脏，不立即重复执行计算；下一次读取 `.value` 时才重新求值，并把当前读取者关联到 computed。缓存依赖于依赖追踪，计算函数应该保持纯净；有副作用的操作放在 `watch` 或显式方法中。

### 4.5 `watch` 和 `watchEffect` 有什么区别？

**回答：**“watch 适合我明确知道要监听哪个值，还需要新旧值；watchEffect 会自动收集同步执行时读到的依赖。做异步请求时，两者都要考虑上一次请求回来得更晚的问题。”

**追问展开：** `watch` 明确指定数据源，可以拿到新旧值，并控制深度和触发时机；`watchEffect` 运行时自动追踪同步读取到的依赖，适合简单的副作用。异步回调中 `await` 之后才读取的响应式值不会按同样方式被自动追踪；请求竞态要通过 cleanup 或请求 ID 处理。

### 4.6 Vue 为什么异步批量更新 DOM？`nextTick` 等待什么？

**回答：**“同一轮里连续改几次状态，Vue 会把组件更新排队并去重，最后统一更新 DOM。nextTick 等的是这轮更新结束，方便我随后读取 DOM；它不保证浏览器已经绘制完，也不等网络请求。”

**追问展开：** 如果要等动画真正绘制，`nextTick` 之后还要考虑 `requestAnimationFrame`；如果要等接口结果，应等待请求本身。这三个“等”解决的是不同阶段的问题。

### 4.7 Vue 的编译优化做了什么？

**回答：**“Vue 编译模板时会找出哪些部分不变、哪些部分会变。运行时就能少比较静态内容，重点更新动态节点和属性。面试里我会讲这个思路，不背具体标志位数字。”

**追问展开：** 编译器把模板变成 render 函数，并标记静态节点、动态属性和动态子节点。运行时可优先比较会变化的部分，减少无效遍历。`patchFlag`、静态提升和 block tree 都服务于这个目标；具体标记值不是面试重点。

### 4.8 Vue 列表为什么需要稳定 key？

**回答：**“列表的 key 是节点身份。插入或排序时，有稳定 key 才能把原来的组件状态跟正确的数据项对应上。会变化的列表用索引当 key，输入框内容就可能串到另一行。”

**追问展开：** key 表示同层节点身份，帮助 patch 算法在插入、删除和移动时复用正确的组件实例与 DOM。索引 key 在会重排的列表中可能使输入状态串位。Vue 3 的 keyed diff 会结合首尾同步、映射查找和最长递增子序列，减少需要移动的节点。

### 4.9 最长递增子序列在 Vue keyed diff 中的作用？

**回答：**“Vue 在调整列表时，会找出一段相对顺序本来就正确的节点，这些节点可以不移动。最长递增子序列就是帮它找到这部分，减少 DOM 移动。”

**追问展开：** 对新旧列表中能复用的节点建立旧位置序列，最长递增子序列代表相对顺序已经正确的节点；这些节点可以保持原位，其余节点再移动或新增。它是减少 DOM 移动的优化，不是整个 Diff 过程的唯一算法。

### 4.10 为什么 `setup()` 中的普通局部变量变化不会更新视图？

**回答：**“setup 里的普通变量变了，Vue 没办法知道，也不会自动更新页面。要让视图跟着变，就把它放进 ref 或 reactive，再让模板或 effect 读取它。”

**追问展开：** 普通变量读写没有经过响应式代理或 ref 的 getter/setter，Vue 无法收集依赖和触发更新。需要用 `ref/reactive` 表达会影响界面的状态，或者通过外部 store 提供可追踪的订阅机制。

### 4.11 Vue 组件更新的调度为什么要去重？

**回答：**“多个状态在同一轮里变化时，Vue 会把组件更新先排进队列，重复的更新合并处理。这样改三次状态通常不用 patch 三次 DOM，调度时还要保证父子组件的合理顺序。”

**追问展开：** 去重之外，调度器还要维护父子更新顺序和递归更新边界；源码阅读入口见 §8.1。面试官若问“为何是微任务”，可从本轮同步状态修改完成后统一刷新来解释。

### 4.12 Vue 2 与 Vue 3 的 `v-model` 机制怎么理解？

**回答：**“v-model 可以理解为父组件把值传下去，子组件通过更新事件把新值报上来。Vue 3 默认是 modelValue 和 update:modelValue；子组件不能直接改父组件传来的 prop。”

**追问展开：** Vue 2 常见默认约定是 `value/input`，Vue 3 支持具名 model，比如一个组件分别绑定标题和可见状态。无论哪版，子组件都通过事件请求父组件更新，不直接改 prop。


### 4.13 effect 为什么要在重新执行前清理旧依赖？

```ts
effect(() => {
  console.log(state.ok ? state.a : state.b);
});
```

**回答：**“effect 每次运行都会重新收集它这次真正读到的属性。比如条件从读 a 改成读 b，旧的 a 依赖要清掉；不然以后改 a 还会触发无关更新。”

**追问展开：** 第一次 `ok` 为真时会读取 `ok` 和 `a`；切换为假后只应依赖 `ok` 和 `b`。若不从旧依赖集合移除 effect，后续修改 `a` 仍会触发无关更新。实际实现会记录每个 effect 订阅过的依赖集合，在重新收集前清理，并避免清理和触发过程中重复执行。

### 4.14 `shallowRef`、`shallowReactive` 为什么存在？

**回答：**“大对象如果每一层都代理，会有额外成本。数据主要整体替换时，我会考虑浅响应式；但这时直接改深层字段不会触发更新，必须按它的更新方式来选。”

**追问展开：** 深层响应式会递归代理对象，适合细粒度更新，但对大对象或外部不可变数据会有额外成本。浅响应式只追踪顶层或 `.value` 的变化，适合整体替换的数据；代价是直接修改深层字段不会触发预期更新。选择取决于数据的更新方式。

### 4.15 `KeepAlive` 缓存的是什么？

**回答：**“KeepAlive 会保留组件实例，切回来时能恢复原来的表单或滚动状态。代价是占内存，而且停用时订阅和计时器要处理好，不能以为它等于销毁。”

**追问展开：** `KeepAlive` 缓存动态组件的 vnode 和组件实例，切换时可停用而非销毁，再次激活时复用状态。它适合标签页、表单返回等场景，但缓存过多会占内存；需要通过 `include/exclude/max` 和激活、停用生命周期管理副作用。它不等于把所有请求结果永久缓存。

### 4.16 Vue renderer 如何把 vnode 变成真实节点？

**回答：**“renderer 先看 vnode 是元素、文本还是组件，再决定怎么挂载；更新时比较新旧 vnode，修改属性、子节点或移动节点。理解挂载、更新、卸载这条链比背内部函数名更有用。”

**追问展开：** Vue 把创建节点、插入、移除等宿主操作抽象成接口，所以 renderer 核心可以适配 DOM 以外的目标。现场画调用链时从 `mount → patch → unmount` 展开即可。

## 5. React 工程实践题

这组题问的是实际写页面时如何取舍，例子与 PersonalHub 的实现无关；框架内部机制放在 §7。

### 5.1 React 项目如何组织页面和组件？

**回答：**“我先按业务页面拆，再把稳定的交互抽成组件。比如搜索框可以复用，但订单列表和用户列表的筛选、请求状态各自管理，不会为了共用一个框把两页的业务逻辑塞在一起。”

**追问展开：** 页面负责业务编排，领域组件负责某一块完整 UI 和状态，共享组件只放稳定、低业务耦合的能力。组件拆分应以职责和状态边界为依据，不能为了减少文件行数过度拆分。

### 5.2 `useState`、`useEffect` 和 `useRef` 分别怎么用？

**回答：**“需要显示在界面上的值用 useState；请求和订阅放 useEffect，并记得清理；跨渲染保存但不用触发界面更新的值用 useRef。”

**追问展开：** 比如计时器 ID 放 ref，计时器显示的秒数放 state；订阅计时器放 effect，依赖变化或卸载时清理。能在渲染时根据 props/state 直接算出的值，不必再用 effect 存一份。

### 5.3 React 中如何避免异步请求竞态？

**回答：**“参数切换时，我会取消旧请求，同时给每次请求一个身份标记。结果回来再核对它是不是当前这次；只调用 abort 不够，因为请求可能已经完成。”

**追问展开：** 一个可演示的例子是：先搜索 A，马上改成 B，A 的结果却晚于 B 返回。只有结果所属的查询词或 requestId 仍是当前值时才更新界面。

### 5.4 `useMemo` 和 `useCallback` 应该什么时候使用？

**回答：**“useMemo 缓存计算结果，useCallback 保持函数引用。我要先确认重新计算或引用变化真的有成本，再加它们；否则依赖更复杂，收益可能很小。”

**追问展开：** 用 Profiler 先看是哪一块耗时。即使加了缓存，依赖写错也会读到旧值；对象或回调只传给普通 DOM 节点时，稳定引用通常没有实际收益。

### 5.5 如何理解受控组件和非受控组件？

**回答：**“受控输入的值在 React 状态里，校验和联动方便；非受控输入主要由 DOM 自己保存，提交时再读取。复杂业务表单我更倾向受控方式或成熟表单库。”

**追问展开：** 文件输入是典型的非受控场景，浏览器不允许直接把文件路径写回输入框。表单库的具体实现也不一定把每次输入都复制进组件 state，别把“用了表单库”和“所有字段都受控”画等号。

### 5.6 为什么要封装请求 Hook？

**回答：**“我封装请求 Hook 是为了把 loading、错误处理和响应格式统一起来。页面只关心业务数据，不需要每个页面都猜一次服务端返回的结构。”

**追问展开：** 封装要先确认请求库拿到的是原始响应、响应信封还是业务数据，否则容易二次解包。重试也要区分读请求和可能产生副作用的写请求。

### 5.7 React 页面如何处理 loading、empty、error 三种状态？

**回答：**“加载中、成功但没数据、请求失败和没有权限是四种不同情况。页面要分别给骨架、空态、重试和 403 提示，不能把所有情况都渲染成‘暂无数据’。”

**追问展开：** “空”必须以一次成功响应为前提。请求失败却清掉旧数据时，最好说明旧内容是否仍可看；403 不应被“暂无数据”掩盖。

### 5.8 为什么要使用 React.lazy 和代码分割？

**回答：**“地图、富文本编辑器这类首屏用不到的重组件，我会在用户打开时再加载。这样首屏少下载一部分代码，但要给等待界面，也要处理资源加载失败后的重试。”

**追问展开：** 常见拆分边界是路由和低频重组件。发布后旧页面请求已经换名的 chunk 可能失败，恢复入口可以提示刷新；收益需要看构建产物与首屏网络记录。

### 5.9 Error Boundary 能捕获哪些错误？

**回答：**“Error Boundary 能兜住子组件渲染过程中的错误，但点击事件或异步请求报错不会自动进来。这两类错误仍要在事件处理和请求层处理。”

**追问展开：** Boundary 放得太高，一处报错会让整页都进入兜底；放在容易出错的功能区旁边，可以只重试那一块。自身抛出的错误要由更外层 Boundary 处理。

### 5.10 如何设计可复用的复杂输入组件？

**回答：**“我先定义组件真正共用的输入、输出和交互，再让业务差异通过 props 和回调传进来。组件如果直接知道某个页面的 API 和状态，后面就很难复用。”

**追问展开：** 可复用组件要稳定的是交互契约和结构，变化的业务行为通过 props、受控值和回调注入。组件不能为了复用而知道过多业务细节，否则一个页面的状态变化会影响其他页面。

### 5.11 ProTable 和普通 Table 怎么选？

**回答：**“标准的后台列表有筛选、分页、刷新和工具栏时，ProTable 能省不少代码。展示特别定制或结构很简单时，普通 Table 更直接。”

**追问展开：** 选 ProTable 时，接口分页、排序和筛选参数要在 `request` 边界转换清楚；如果表格是自定义单元格编辑、复杂拖拽或特殊虚拟滚动，先评估普通 Table 是否更容易控制。

### 5.12 React 页面如何做性能优化？

**回答：**“我会先测问题在哪：加载慢看包体积和首屏指标，操作卡看渲染和长任务，请求慢看接口耗时。优化后用同口径数据比较，不凭感觉说变快。”

**追问展开：** 前端性能优化通常按加载、运行和网络三个方向处理：代码分割和资源压缩降低加载成本；减少无效渲染和大列表更新降低运行成本；缓存、请求合并和接口分页降低网络成本。优化需要指标验证，例如 LCP、INP、CLS、首屏 JS 和接口 p95。

### 5.13 React 响应式布局为什么还需要 JavaScript？

**回答：**“CSS 可以改排列和宽度；导航变抽屉、按钮进更多菜单这种交互结构变化，需要 React 根据视口来切。断点最好统一维护，避免 JS 和样式判断不一致。”

**追问展开：** CSS 适合处理布局，JavaScript 适合处理交互模式和组件树变化。不要使用 User-Agent 判断设备，应根据视口和能力决定布局，同时处理 resize、固定底栏、安全区和内容溢出。

### 5.14 React 中如何处理主题切换？

**回答：**“主题切换我会把颜色等基础值做成 token 或 CSS 变量，再统一传给浮层和图表。还要明确用户偏好与站点默认配置谁优先，避免刷新时闪一下。”

**追问展开：** 主题系统通常使用 CSS Variables 或 Design Tokens，把颜色、间距和字体集中管理。主题状态要区分服务端默认配置和用户本地覆盖，切换时要避免闪烁，并确保 Drawer、Modal、图表等浮层使用同一套 token。

### 5.15 React 前端如何处理权限？

**回答：**“前端权限主要让用户看到自己能做什么，安全检查必须留在后端。即使按钮被隐藏，别人也可能直接发接口请求。”

**追问展开：** 前端权限控制主要改善用户体验，后端权限控制才是安全边界。前端可以做路由守卫、菜单过滤和按钮显隐，但所有敏感接口必须由后端重新鉴权。

### 5.16 为什么不能把所有数据都放进 React 全局状态？

**回答：**“只有真正跨页面共享、生命周期长的状态才放全局。输入框留在组件，接口列表交给服务端状态管理；不然刷新和错误处理会越来越难。”

**追问展开：** 全局状态适合真正跨页面共享且生命周期较长的数据。服务端数据应该保留请求、缓存、刷新和错误信息，不能简单复制成全局变量。状态归属越清晰，组件越容易测试和复用。

### 5.17 如何回答“React 和 Vue 的区别？”

**回答：**“Vue 的模板和响应式机制比较集中，React 更偏向用 JavaScript 组合组件。选型我会看团队经验、组件库和交付需求，不会说某一个框架天然更好。”

**追问展开：** 追到状态更新机制时，可以举同一个表单联动例子：Vue 追踪读取到的响应式属性，React 则由 state 更新触发组件重新执行。两边都能完成需求，真正影响项目的是现有组件库、SSR 方案和团队维护成本。

## 6. React 状态与渲染基础题

这些问题属于 React 面试常见基础题。回答时先讲通用原理，再根据自己的实际经历举例。

### 6.1 React 的核心思想是什么？

**回答：**“我会把 React 理解为‘状态决定界面’。我写组件描述当前状态下应该长什么样，状态变了 React 重新计算，再把必要变化更新到页面。”

**追问展开：** React 用组件描述 UI，用 props 传入外部数据，用 state 表示内部变化。状态发生变化时，React 重新计算组件树，并把必要的变化提交到真实 DOM。它强调声明式 UI、单向数据流和组件组合。

### 6.2 React 为什么强调单向数据流？

**回答：**“数据从父组件传给子组件，子组件要改数据时通过回调通知父组件。这样我能比较容易找到状态到底由谁负责。”

**追问展开：** 如果两个兄弟组件都要改同一份数据，通常把状态提升到最近的共同父组件，或放入明确的共享状态层；避免两边各维护一份后再手动同步。

### 6.3 Context、Redux 和服务端状态工具怎么选？

**回答：**“主题和语言这种低频依赖可以放 Context；复杂的跨页面客户端状态再考虑 Redux；接口列表更适合有缓存和刷新机制的服务端状态工具。关键是看数据来源和更新频率。”

**追问展开：** Context 适合主题、语言、当前用户等低频全局依赖；Redux 适合复杂、可追踪、跨页面共享的客户端状态；服务端状态工具适合缓存、请求、刷新和错误。不能把接口列表一律放 Redux，也不能用 Context 承载高频变化的大对象。

### 6.4 `React.memo` 有什么作用？

**回答：**“memo 能在父组件重渲染但子组件 props 没变化时跳过一次渲染。不过对象和函数每次新建仍会让比较失败，组件自己的 state 变化也照样会渲染。”

**追问展开：** 默认比较是对每个 prop 做 `Object.is`，不深比较。使用前用 Profiler 看子组件是否真的耗时；若 Context 变了，哪怕 props 没变，读取 Context 的组件也会更新。

### 6.5 为什么列表渲染需要 key？

**回答：**“key 告诉 React 这行数据是谁。列表会排序或增删时，我用稳定的业务 ID；用索引可能让某一行的输入状态跑到另一行。”

**追问展开：** key 用于帮助 React 判断列表项是否是同一个实体，从而复用对应组件实例和 DOM。key 在同一组兄弟节点中应稳定且唯一，通常使用数据库 ID。会排序、插入或删除的列表不要用数组 index 作 key，否则可能出现输入框状态错位。

### 6.6 React 中如何处理表单？

**回答：**“简单表单我用 state 控制；字段多、校验复杂时用表单库。提交时要处理重复点击、服务端错误、成功后的刷新，以及用户取消后草稿怎么处理。”

**追问展开：** 前端校验只负责及时反馈；服务端仍需检查权限、数据类型和业务约束。保存失败时保留用户输入，比一律重置表单更容易恢复。

### 6.7 如何设计错误恢复入口？

**回答：**“先判断是哪类错误：渲染崩溃交给 Error Boundary，请求失败给重试，权限不足给 403，资源加载失败给重新加载。恢复入口要放在用户能重新操作的位置。”

**追问展开：** 渲染错误使用 Error Boundary；请求错误使用 request 层和页面 error state；权限错误使用 403 状态；网络断开使用离线提示；懒加载 chunk 失败提供重新加载。不同错误要放在能恢复它的层级处理，不能只用一个全局 try/catch。

### 6.8 写请求超时后，能直接重试吗？

**回答：**“不能直接假设上一次失败了。浏览器超时或 abort，只说明我没拿到结果，服务端可能已经写成功。我会先查这次操作的状态；需要重试时，用同一个幂等键让服务端识别它是同一次提交。”

**追问展开：** 读请求的旧结果是否能更新页面，是请求竞态问题，见 §5.3；写请求还涉及服务端是否已经提交。重试应有业务身份和去重规则，不能把“取消了前端请求”当成“服务端回滚了”。

### 6.9 SSR、CSR 和 Hydration 是什么？

**回答：**“CSR 主要在浏览器渲染；SSR 先在服务端生成 HTML；Hydration 是 React 在浏览器接管这份 HTML。做 SSR 时我会特别注意两边首次输出必须一致。”

**追问展开：** SSR 能让爬虫和用户更早拿到 HTML，但还要下载与执行客户端代码才能完成交互。Hydration 若遇到时间、随机数或本地存储造成的首次输出差异，要先让两边初始内容一致，细节见 §7.14。

### 6.10 React 中如何避免不必要的重新渲染？

**回答：**“我先找哪块状态变化导致了重复渲染，再决定是把状态下沉、拆组件，还是用 memo 和稳定引用。看到一次渲染就加缓存，通常没有意义。”

**追问展开：** 先确认是哪一层 state 变化造成渲染，再通过状态下沉、组件拆分、稳定 props、`React.memo`、`useMemo`、`useCallback`、虚拟列表和批量更新解决。不能一看到渲染就盲目加 memo。

## 7. React 源码题和回答

源码题重点是解释“状态如何保存、更新如何调度、节点如何复用”。下方短片段用于说明现象；完整可运行的教学模型在 §8，不能把它说成 React 源码原文。

### 7.1 为什么 `setState` 后立即读取 state 还是旧值？

```tsx
import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

**回答：**“因为这个事件处理函数拿到的是本次渲染时的 count 快照。setCount 安排下一次更新，不会改掉当前函数里的变量，所以紧接着打印还是旧值。”

**追问展开：** 如果下一次更新依赖前一次结果，就把计算交给更新队列，而不是读取当前闭包里的旧值：

```tsx
setCount((current) => current + 1);
```

### 7.2 为什么连续三次 `setCount(count + 1)` 可能只加一？

```tsx
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);
```

**回答：**“这三次都用同一个旧 count 算出同一个新值，相当于重复设置同一个数字。想累加三次，就写函数式更新，让每一步拿到前一步算出的结果。”

**追问展开：** 用函数式更新可以让每一步接收上一步算出的值：

```tsx
setCount((value) => value + 1);
setCount((value) => value + 1);
setCount((value) => value + 1);
```

### 7.3 React 为什么要批量更新？

**回答：**“React 把同一轮里的多个更新一起处理，能少做几次渲染和 DOM 提交。批处理不是丢更新；如果后一个更新依赖前一个结果，我会用函数式写法。”

**追问展开：** React 18 以后，Promise 回调和定时器等更多场景也会自动批处理。若确需同步提交 DOM，可研究 `flushSync`，但它会增加同步工作，不应作为常规写法。

### 7.4 `useState` 的 Hook 状态如何按顺序对应？

完整可运行的数组槽位模型见 [createHooks](./examples/interview-models.mjs)，运行与断言见 [测试](./examples/interview-models.test.mjs)。现场手写可先画出“组件实例 → Hook 顺序 → 每个 Hook 的更新队列 → 下一次 render 取值”，再写代码；不要把数组槽位说成 React 的真实存储结构。

**回答：**“Hook 状态保存在组件对应的 Fiber 上，每次渲染按调用顺序取。React 不是根据变量名匹配 Hook，所以不能把 Hook 放进条件分支，让顺序一会儿变一会儿不变。”

**追问展开：** 真实 React 的当前 Fiber 使用 Hook 链表及更新队列；教学模型用数组和游标表达“按位置对应”这一点。条件 Hook 会让后续位置错位，因此规则要求顶层稳定调用。

### 7.5 `useEffect` 为什么要返回 cleanup？

```tsx
useEffect(() => {
  const controller = new AbortController();
  loadData({ signal: controller.signal });
  return () => controller.abort();
}, [contentId]);
```

**回答：**“effect 如果订阅了事件、开了定时器或发了可取消请求，依赖变化和组件卸载时都要清理。否则旧逻辑还在跑，容易出现重复订阅或旧结果回写。”

**追问展开：** 清理函数会在下一次相关 effect 建立前运行，卸载时也会运行。请求取消还应结合请求身份校验，避免已完成的旧回调覆盖新页面。

### 7.6 `useEffect` 为什么不能直接返回 Promise？

```tsx
// 不推荐
useEffect(async () => {
  await loadData();
}, []);
```

**回答：**“effect 约定返回清理函数，而 async 函数一定返回 Promise，所以不能直接把 effect 回调写成 async。我会在里面定义异步函数，然后正常返回 cleanup。”

**追问展开：** 正确写法是把异步函数放在 effect 内部，外层仍同步返回清理函数：

```tsx
useEffect(() => {
  let active = true;
  async function run() {
    const result = await loadData();
    if (active) setData(result);
  }
  void run();
  return () => {
    active = false;
  };
}, []);
```

### 7.7 React Diff 为什么需要 key？

**回答：**“key 帮 React 判断新旧列表中哪一项还是同一项。它能让对应的组件状态继续跟着正确的数据；排序列表用索引当 key，很容易把输入状态放错行。”

**追问展开：** key 的作用范围是同一组兄弟节点；它决定组件身份和 state 复用。稳定不等于全局唯一，在这组列表里唯一即可。

### 7.8 Fiber 解决了什么问题？

**回答：**“Fiber 把组件更新拆成可以保存进度的工作单元。这样 React 在一些更新里能先响应更紧急的操作，再继续低优先级渲染；它不是开了一个新线程。”

**追问展开：** Fiber 节点保存当前更新的进度与关联信息。调度器可以在 render 阶段暂停、继续或放弃一部分工作，commit 阶段再集中提交变化。JavaScript 仍在主线程运行；如果组件本身做了很重的同步计算，Fiber 也不会替它省掉计算量。

### 7.9 React Scheduler 为什么重要？

**回答：**“调度器负责决定哪些更新先做、哪些可以稍后做。比如输入要立刻跟手，庞大结果列表可以延后；但调度不会让那段计算本身凭空变快。”

**追问展开：** 例如搜索框输入和结果列表都要更新时，输入应先跟手，结果可以稍后呈现。这依赖更新优先级和可中断的 render；若列表计算本身很慢，还要拆分计算、分页或做虚拟列表。

### 7.10 React 事件系统有什么特点？

**回答：**“React 把事件处理做了统一封装，并在根节点附近集中监听。开发时我重点看事件冒泡、阻止默认行为，以及自己额外加在 window 上的监听有没有清理。”

**追问展开：** React 通过事件委托和 SyntheticEvent 封装浏览器事件，使事件行为和跨浏览器差异更统一。事件会沿组件树执行捕获和冒泡。开发时要注意 `stopPropagation`、默认行为、事件回调引用和组件卸载后的监听清理。需要监听窗口或 DOM 节点时，应在 effect 中注册并在 cleanup 中移除。

### 7.11 `React.memo` 为什么有时不起作用？

```tsx
import { memo, useState } from 'react';

const Child = memo(function Child({ options }: { options: { title: string } }) {
  return <div>{options.title}</div>;
});

export function Parent() {
  const [count, setCount] = useState(0);
  return <>
    <button onClick={() => setCount((value) => value + 1)}>{count}</button>
    <Child options={{ title: 'AI' }} />
  </>;
}
```

**回答：**“这个例子里父组件每次都创建一个新 options 对象，memo 比较时看到引用变了，子组件就会重渲染。可以直接传 title 这样的基础值，或者在确有收益时稳定对象引用。”

**追问展开：** `memo` 默认逐项用 `Object.is` 比较 props，不会深比较对象。先量一下 Child 是否真有渲染成本；为了“修复 memo”而增加复杂依赖，可能得不偿失。

### 7.12 为什么 Context 可能导致大范围重新渲染？

**回答：**“Provider 的 value 一变，读取它的组件就可能更新。如果把高频输入和很多无关状态都塞进一个 Context，影响面会很大；我会拆 Context 或让状态靠近使用它的组件。”

**追问展开：** 把“主题”和“逐字变化的输入”放在同一个 value 里，就会扩大更新范围。拆 Context 或让输入状态靠近输入框；只把 value 包进 `useMemo`，若其中字段每次都变，仍无法解决问题。

### 7.13 React 为什么需要 `key` 而且不能随意改变？

**回答：**“key 变了，React 会认为这是另一个组件，原来的 state 也会被重置。主动重置表单时可以利用这一点；普通列表千万别每次随机生成 key。”

**追问展开：** 换 key 重置表单是有意让 React 创建新实例；若只想清空一个字段，直接更新字段状态更清楚。随机 key 会导致每次渲染都丢掉整行状态。

### 7.14 Hydration 不一致是什么问题？

**回答：**“服务端输出的 HTML 和浏览器第一次渲染结果不一样，就会出现 hydration 不一致。常见原因是首次渲染读了时间、随机数或 localStorage；我会让首屏数据先一致，再在 effect 里读浏览器专属信息。”

**追问展开：** 如果首屏必须依赖用户时区或本地偏好，要么服务端拿到同一份初始值，要么先渲染双方一致的占位内容，接管后再更新；单纯压掉警告不会修好不一致。

### 7.15 如何手写一个简化版 `useMemo`？

完整可运行的 `useMemo` 教学模型也在 [createHooks](./examples/interview-models.mjs) 中；[测试](./examples/interview-models.test.mjs) 覆盖依赖不变、变化、空值和计算异常。面试时可从“每个 Hook 位置保存上次依赖和值”写起，再补依赖比较与初始化标记。

**回答：**“我会给每个 Hook 位置保存上一次的值和依赖。下一次依赖逐项相同，就直接返回缓存；不同才重新算。初始化要有单独标记，不能把 0 或 false 当成‘没缓存’。”

**追问展开：** 依赖逐项用 `Object.is` 比较；factory 抛错时不能把失败结果写入缓存。真实 React 仍可能重新计算，所以业务正确性不能依赖缓存永不失效。

### 7.16 如何手写一个简化版事件总线？

实现与边界测试见 [可运行教学模型](./examples/interview-models.mjs) 的 `createEmitter` 和 [测试](./examples/interview-models.test.mjs)。

关键规则：每次订阅有独立条目；取消函数通过 `disposed` 保证可重复调用；删除空集合前检查它仍是当前集合；发布遍历快照，本轮新增订阅在下一次发布生效。监听器抛错会向发布方传播，本模型未实现错误隔离。


**回答：**“事件总线就是按事件名保存监听函数。订阅要返回取消函数，发事件时通知当前监听者；取消最好允许重复调用。React 组件里订阅后，一定在 effect 清理时退订。”

**追问展开：** 发布期间取消订阅时，是否影响本轮剩余回调，需要先约定语义。示例采用快照：本轮名单固定；监听器抛错会向发布方传播，没有做隔离。

### 7.17 React 的 render 阶段和 commit 阶段分别做什么？

**回答：**“render 阶段计算下一版界面，可能重做或被放弃；commit 阶段才把变化写到 DOM。所以我不会在 render 里发请求或改外部对象，副作用放事件处理或 effect。”

**追问展开：** render 可以被中断或重做，因此组件函数应保持纯净。commit 会应用 DOM 变化并处理相应 Effect；已经开始的一次 commit 不会像 render 那样让出执行权。若在 render 中发请求，重做时就可能发出重复请求。

### 7.18 更新队列如何处理“值更新”和“函数式更新”？

```tsx
setCount(5);
setCount((n) => n + 1);
// 这一批更新按顺序计算，最终是 6。
```

**回答：**“更新队列按顺序算。setCount(5) 先指定 5，后面的函数式更新拿到 5 再加 1，结果就是 6。依赖当前值时用函数形式，避免读到旧快照。”

**追问展开：** 可以把队列当作一串“覆盖为某值”或“用前一步结果计算”的指令。这个例子先覆盖为 5，再加 1。若一批更新包含不同优先级，React 可能分多次渲染处理；面试回答重点仍是依赖前一步结果时使用函数式更新。

### 7.19 Lane 和 `useTransition` 解决什么问题？

**回答：**“transition 是告诉 React：这次更新可以晚一点，先让输入等紧急交互保持响应。它适合搜索结果或大列表，不适合拿来延迟受控输入框自己的值。”

**追问展开：** Lane 是 React 内部表示更新优先级的方式。`useTransition` 标记可延后的更新；若用户继续输入，旧的结果渲染可以被打断。输入框自己的值仍要立即更新，重计算或网络请求的成本也要单独处理。

### 7.20 `useDeferredValue` 和防抖有何区别？

**回答：**“useDeferredValue 让某个消费者暂时用稍旧的值，优先保证当前输入流畅；防抖则等固定时间不再输入后才执行。前者不自动减少请求数，后者通常会减少触发次数。”

**追问展开：** 假设输入框一变就筛选一万行：deferred value 可以让输入先显示新值，列表暂时沿用旧值。若需求是停止输入 300 毫秒后才请求接口，应使用防抖；deferred value 自己不会保证少发请求。

### 7.21 `useEffect` 和 `useLayoutEffect` 的执行时机？

**回答：**“布局 effect 在 DOM 更新后、浏览器绘制前运行，适合必须先量尺寸再调整的场景；普通 effect 更适合请求和订阅。布局 effect 会挡住绘制，我只在确实需要时用。”

**追问展开：** 例如弹层要先量位置再避免闪动，才考虑 layout effect；普通数据请求放 effect 即可。layout effect 里的同步工作越多，用户越晚看到这一帧；服务端也没有 DOM 可测。

### 7.22 Strict Mode 为什么会让开发环境的 Effect 看起来运行两次？

**回答：**“开发环境的 Strict Mode 会额外跑一次 effect 的建立和清理，帮我发现订阅没清干净的问题。应该把 setup 和 cleanup 写对，而不是用 ref 绕过检查。”

**追问展开：** 生产环境不会因 Strict Mode 自动增加这一轮。可以拿 WebSocket 订阅来检查：建立连接后返回关闭连接的 cleanup，重新挂载时不应留下两条连接。

### 7.23 React 为什么不保证 `useMemo` 是语义上的永久缓存？

**回答：**“useMemo 是性能优化，不是永久存储。React 可能重新计算它，所以业务正确性不能依赖‘这个函数只运行一次’；要保存稳定实例，我会用 ref 或 state。”

**追问展开：** 例如 WebSocket 实例需要明确创建和清理，不能靠 `useMemo(() => new WebSocket(...), [])` 假设只执行一次；这类外部资源应由 effect 管生命周期。

### 7.24 为什么不能在 render 中直接修改外部对象？

**回答：**“render 可能被重复执行或中途放弃，如果这时先改了外部对象，界面和外部状态就可能对不上。所以 render 只负责算界面，真正的写入放事件处理或 effect。”

**追问展开：** 如果多个组件要读取同一个外部可变对象，还要提供订阅和一致的快照接口；仅把对象放在模块变量里，React 不知道何时更新视图。

### 8.2 React 更新队列和 memo：如何现场展开？

[教学模型](./examples/interview-models.mjs) 的 `createHooks` 提供完整的 `render/useState/useMemo`。每个实例模拟一个组件，按调用顺序保存槽位；setter 只入队，下次手动 render 按顺序计算。三个值更新使用同一快照只加一次，三个函数更新累积三次。memo 用独立初始化标记，依赖逐项 `Object.is`，不传依赖每次计算；factory 抛错不写缓存。

**边界：** 不支持组件树、条件 Hook、React lane、自动调度或并发回放。渲染必须遵守相同 Hook 顺序。状态更新成本与队列长度相关，memo 比较成本与依赖长度相关。可用它解释机制，不能用它替换 React。

### 8.3 Vue 分支依赖：如何现场展开？

`createReactivity` 提供 Proxy、effect、依赖收集、分支清理和停止订阅。当 `ok ? a : b` 从真切到假时，旧 a 依赖被清除；修改 a 不再触发。触发时先复制订阅集合，避免执行中清理再添加导致遍历重复。effect 使用 try/finally 恢复外层上下文。

**边界：** 只演示普通对象已有属性的浅层读写；没有数组、Map/Set、删除/遍历依赖、computed、调度去重。清理成本取决于该 effect 的依赖数，通知成本取决于该属性的订阅数。真实 Vue 3.5 的内部数据结构更复杂。

### 8.4 并发限制器：完整答案和复杂度

`runLimited(tasks, limit)` 接收惰性任务函数，启动最多 limit 个 worker；每个 worker 顺序领取索引，失败保存 rejected 结果并继续，全部结束后按输入顺序返回。空数组返回空结果，非正整数 limit 拒绝，同步抛错与异步拒绝统一处理。

**取舍：** 这里选择 allSettled 语义；不实现取消或首错立即终止。传入已经启动的 Promise 无法控制其启动并发。调度工作量 O(n)，结果空间 O(n)，同时运行任务数最多 min(n, limit)。
