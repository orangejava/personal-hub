## 1. 项目一句话介绍

### 面试问题

请介绍一下你的 PersonalHub 项目。

### 项目版答案

**口述：**“PersonalHub 是我个人主导的知识中台和 AI 工具箱。用户端可以读内容、管理资料和使用 AI 工具，管理端负责内容、用户和权限。我用 AI Agent 作为主要开发工具，参与前后端方案、编码和自查；架构取舍与验收由我负责。项目里最值得讲的是登录权限、AI 流式对话，以及上传和异步任务这几条前后端链路。”

**技术展开：** PersonalHub 包含用户端、后台管理端和 NestJS 后端：用户端负责公开内容、内容阅读、登录后工作区和 AI 工具；管理端负责用户、角色、权限、内容审核、文件和系统配置；后端使用 NestJS、Prisma 和 PostgreSQL，Redis 用于会话缓存和限流，对象存储用于文件，BullMQ 用于小册导入和 AI 图片/视频任务。

项目中我重点解决了几类跨层问题：两个前端应用之间的登录态恢复、JWT/RBAC 权限控制、AI 对话 SSE 流式输出、AI 额度预占与结算、私密内容授权、预签名上传和异步任务可靠性。

### 通用版答案

“我介绍全栈项目会先讲它解决什么问题，再讲前端、后端和数据怎么配合。接着说自己负责的链路、遇到的难点和实际结果。技术栈只在解释取舍时提，不会把框架名字念一遍当作项目介绍。”

### 追问提醒

- 当前已完成：React/Umi 用户端、React/Umi 管理端、Nest M0-M6 主链路和首版部署主线。
- 规划或占位：Next.js 迁移、Flutter、语音输入、提示词优化、部分真实媒体模型接入。

### 简历补充问题：富文本、PDF、Word 和 Markdown 阅读如何处理？

**项目版答案：**“我把内容先按类型建模。Markdown 和富文本读正文，PDF、Word 则关联上传的主文件，在阅读页用对应预览器打开。PDF 和 Word 预览组件按需加载，避免所有用户首屏都下载预览库。这里的 Word 是 `.docx` 在线预览和下载，不是站内 Word 编辑器。”

## 2. 简历工作内容一：pnpm Monorepo、用户端/管理端拆分和共享类型

### 简历表述

> 项目使用 pnpm Monorepo，拆出用户端、管理端、Nest 服务和共享类型，前后端接口类型放一起维护。

### 面试问题

为什么使用 Monorepo？为什么要拆用户端和管理端？共享类型如何维护？

### 项目版答案

**口述：**“我把用户端、管理端和后端放在同一个仓库，主要是它们会一起改接口和类型。用户端偏内容阅读和 AI 交互，管理端偏表格、表单和权限，所以分开构建。公共部分只放类型、请求封装和 Origin 约定。拆开以后最麻烦的是跨页面恢复登录态：Access Token 放在各自页面内存里，管理端打开时通过 Refresh Cookie 向后端恢复会话。”

**技术展开：**

项目根目录使用 pnpm workspace 和 Turborepo，主要应用位于 `apps/`，共享包位于 `packages/`：

- `apps/user-web`：公开前台、工作区和 AI；
- `apps/admin-web`：运营后台；
- `apps/server`：NestJS API 和独立 Worker；
- `packages/shared-types`：前后端共享的领域类型；
- `packages/api-client`：认证、会话、权限和请求适配；
- `packages/app-origins`：用户端和管理端 Origin 约定。

拆分用户端和管理端是因为两边的信息架构、权限菜单、发布节奏和性能边界不同。用户端强调公开内容和交互体验，管理端强调表格、表单和权限操作。拆分后可以独立构建和部署，也避免管理端代码进入用户端入口。

共享类型放在 `packages/shared-types`，请求封装和 Nest 数据映射放在 `packages/api-client`。前端页面通过 Umi 全局拦截器拿到解包后的业务对象 `T`，不在每个页面重复处理响应信封。

拆分后的关键难点是登录态：用户端和管理端分别运行在 `:8000` 和 `:8001`，Access Token 只在当前页面内存中，管理端打开后通过共享的 HttpOnly Refresh Cookie 调用 `/auth/refresh` 恢复会话。Cookie 类接口按来源白名单校验 Origin；开发代理改写 Origin 时可按 Referer 中的前端来源判断，并非要求两个头同时匹配。

### 通用版答案

“如果几个应用经常一起改接口，Monorepo 能让类型、服务端和调用方在同一次改动里对齐；包管理和构建任务也能统一。关键是把共享边界管住：领域类型和无状态工具适合放公共包，某个页面的业务状态不适合。共享包一变可能影响多个应用，所以构建和测试要按依赖关系跑。”

### 常见追问

**问：Monorepo 会不会导致一个应用改动触发全部应用构建？**

项目通过 workspace 包边界和 Turborepo 任务依赖控制构建范围；实际构建仍需关注共享包变更，因为共享类型或请求包变化可能影响多个消费者。

**问：共享类型是否等于前后端完全类型安全？**

不是。共享 TypeScript 类型能减少字段名和结构不一致，但运行时仍需要 DTO、参数校验、数据库约束和测试。后端不能只信任前端类型。

## 3. 简历工作内容二：JWT/RBAC、Prisma/PostgreSQL、Redis 会话和限流

### 简历表述

> 后端用 JWT/RBAC 做登录校验和权限验证；用户、内容、权限、额度用 Prisma 落到 PostgreSQL；Redis 做会话缓存和接口限流。

### 面试问题

项目的登录认证和权限体系是怎么设计的？

### 项目版答案

**口述：**“登录后，前端拿一个短期 Access Token，刷新凭证放在 HttpOnly Cookie 里。后端保存刷新凭证的哈希值，刷新时会轮换；如果旧凭证又被使用，就撤销会话。权限方面，我把‘能做什么’和‘能操作谁的数据’分开：前端控制菜单和按钮，后端每次仍会查当前权限和资源归属。Redis 主要放会话缓存和限流计数，用户、权限、内容这些核心数据在 PostgreSQL。”

**技术展开：**

项目采用 Access Token + Refresh Token 的会话模型：

1. 登录成功后签发短期 Access JWT；
2. JWT 只携带用户 ID、session ID、authVersion 和 permissionVersion；
3. Refresh Token 通过 HttpOnly Cookie 传输；
4. 数据库只保存 Refresh Token 的 SHA-256 + pepper Hash；
5. 刷新时轮换旧 Refresh Token；
6. 旧 Token 再次出现时视为重放，撤销当前会话。

RBAC 由角色、权限码和数据范围组成。前端权限用于菜单和按钮显示，后端 `PermissionsGuard` 根据当前会话和服务端权限快照重新校验权限，不能信任客户端传来的权限列表。数据范围支持 `OWN` 和 `ALL`，例如普通编辑者只能操作自己的内容，管理角色可以跨作者读取。

PostgreSQL 保存用户、会话、角色、权限、内容、额度和审计数据；Prisma 负责数据访问和事务。Redis 用于会话缓存、登录失败计数、验证码和限流状态，避免每次请求都执行完整的会话查询。

### 通用版答案

“JWT 适合传递短期身份，但光有 JWT 很难处理主动登出和权限变化。一般会用短期 Access Token 配合可撤销、可轮换的 Refresh Token；服务端存刷新凭证的哈希，并在每次请求上重新守住权限边界。Redis 可以放会话缓存和限流计数，用户和权限这些需要持久化、要做事务的数据仍放关系数据库。”

### 常见追问

**问：为什么不把权限列表直接放进 JWT？**

因为 JWT 一旦签发，里面的权限在过期前不会自动变化。项目只放 permissionVersion，真正权限从服务端快照获取，可以让角色权限修改及时生效。

**问：前端隐藏按钮是否足够？**

不够。前端只负责体验，后端必须重新校验身份、权限、数据范围和资源归属。

## 4. 简历工作内容三：预签名上传和 ZIP 导入

### 简历表述

> 文件预签名上传和支持 ZIP 导入。

### 面试问题

项目的文件上传和小册 ZIP 导入是怎么实现的？为什么不让 Nest 直接接收大文件？

### 项目版答案

**口述：**“大文件没有经过 Nest 中转。我先让后端检查上传用途和大小，再给浏览器一个短时有效的上传地址，浏览器直接传对象存储。上传结束后后端会重新检查对象大小和文件内容，不能只信浏览器报的 MIME。ZIP 小册导入比较耗时，所以提交后创建任务交给 Worker；解析时还限制路径、文件数量和解压后的大小，防止恶意压缩包。”

**技术展开：**

上传采用“应用服务创建会话 + 浏览器直传对象存储”的方式：

1. 前端把文件名、大小、用途和 MIME 提交给 Nest；
2. Nest 按用途读取文件策略，检查大小、MIME 和 denylist；
3. 小文件返回单文件预签名 URL，大于 20MiB 的文件走 multipart；
4. 浏览器直接上传到 MinIO 或生产对象存储；
5. 前端把分片 ETag 提交给 complete 接口；
6. Nest 检查对象大小、文件魔数并流式计算 SHA-256；
7. 校验成功后把 `FileAsset` 从 `UPLOADING` 更新成 `READY`。

ZIP 小册导入不会在 HTTP 请求中同步完成，而是创建导入任务并写入 Outbox。独立 Worker 通过 BullMQ 消费任务，解析 `meta.json` 和章节 Markdown。解析器限制路径穿越、章节数量、单章大小和压缩比，避免 ZIP Bomb 和恶意路径覆盖。

数据库写入和 Outbox 事件在同一个事务中完成，dispatcher 再把事件投递到 BullMQ。这样 HTTP 请求不会被长时间占用，Worker 重启后也能继续处理任务。

### 通用版答案

“预签名上传让浏览器直接把文件传到对象存储，应用服务只负责鉴权、签发短时凭证和完成后的校验，能减少文件流量对 API 的占用。大文件可以分片传，完成时按分片信息合并；业务层还要查用途、大小、内容类型和归属。ZIP 导入适合放进后台任务，解析时重点防路径穿越、解压量失控和重试造成的重复写入。”

### 常见追问

**问：为什么要检查魔数？**

扩展名和 MIME 都可以被客户端伪造。魔数来自文件内容的固定字节，可以辅助判断真实类型。

**问：为什么 SHA-256 要流式计算？**

如果先把完整对象读进内存，大文件会造成 Node 堆内存压力。流式计算只保留固定大小的哈希状态和当前 chunk。

**问：ZIP 导入失败怎么办？**

任务记录失败状态和错误信息，源 ZIP 在数据库提交前保留，任务可以重试；Worker 通过 jobId 和任务状态保证处理过程可重入。

## 5. 简历工作内容四：AI 对话 Nest 代理、SSE 和生图/生视频异步任务

### 简历表述

> AI 对话走 Nest 代理 + SSE 流式；生图/生视频走 Outbox + Worker 异步任务，前端主要跟状态和结果。

### 面试问题

AI 对话和图片/视频生成为什么使用两种不同的处理方式？

### 项目版答案

**口述：**“文字对话要让用户马上看到回复，我用 Nest 代理模型流，再通过 SSE 发给前端。图片和视频生成时间长，接口先返回任务，由 Worker 后台执行，前端看状态和结果。文本已接 OpenAI 兼容接口；图片和视频目前默认还是演示 Provider。”

**技术展开：**

AI 对话强调低延迟反馈，用户希望马上看到文字，所以采用同步建立连接、服务端代理上游流式响应的方式：

```text
前端输入
  -> Nest 校验会话、模型、权限、内容引用和额度
  -> OpenAI-compatible Provider
  -> Nest 转换成 STARTED/DELTA/DONE/ERROR
  -> SSE 返回前端
  -> 前端解析并按浏览器帧渲染
```

图片和视频生成通常耗时更长，也可能需要外部任务 ID，因此采用异步任务：

1. API 创建生成任务并预占额度；
2. 业务数据和 Outbox 事件一起提交；
3. dispatcher 把事件投递到 Redis 上的 BullMQ；
4. 独立 Worker 调用图片或视频 Provider；
5. Worker 更新等待中、生成中、成功、失败等状态；
6. 前端查询任务列表或轮询任务状态，并展示结果、下载和历史复用。

这样可以避免长时间占用 HTTP 请求，也便于重试、恢复和失败补偿。当前仓库中 Fake Provider 是默认实现，OpenAI-compatible 文本 Provider 已经实现；不能把所有图片和视频厂商接入说成已经生产化。

### 通用版答案

“选实时流还是异步任务，先看用户要不要边等边看，以及任务会运行多久。文本回复通常用 SSE 单向推给浏览器；图片和视频生成时间不确定，接口更适合先返回任务 ID，再由 Worker 执行。任务状态要持久化，至少能查到当前状态、结果或错误；重试还得避免重复创建和重复扣费。”

### 常见追问

**问：为什么不让 HTTP 请求一直等到图片生成完成？**

因为生成时间不可控，长连接会占用 HTTP 连接，服务重启也容易丢失状态。异步任务可以持久化状态并支持重试。

**问：SSE 网络 chunk 能不能直接 JSON.parse？**

不能。网络 chunk 可能是半个 SSE 事件，也可能包含多个事件，必须先按协议边界组装。

## 6. AI 流式对话的前端难点

### 面试问题

你在 AI SSE 前端处理上遇到过什么问题？

### 项目版答案

**口述：**“流式对话最容易出问题的是把网络分片当成完整消息，以及文字还没渲染完就先显示‘完成’。我先把 SSE 事件拼完整，再把增量文本按帧提交给 React；完成事件要等前面的文字处理完。切换会话时，原来的流继续写回原会话；点停止时先保留已经收到的文字，再等服务端确认停止。”

**技术展开：**

项目中有三个关键问题。

第一，网络 chunk 不是 SSE 事件边界，所以 `aiSse.ts` 会处理半包、多包、CRLF/LF、多行 `data` 和 EOF 尾帧。

第二，不能每收到一个增量就立即更新 React。项目使用 `createAiStreamRenderScheduler`，按 requestAnimationFrame 分批提交文本，防止大段输出导致页面卡顿。

第三，服务端的 `DONE` 事件可能先于浏览器把队列中的文本绘制完，因此终态事件会排在文本队列后面；用户点击停止时先 flush 已收到内容，再请求服务端显式停止；收到终态前保留流和并发名额，停止失败允许重试。

此外，新建会话首次发送时还要区分“占位会话绑定真实 ID”和“用户主动切换已有会话”，否则 effect cleanup 会误取消请求并清空当前消息。

### 通用版答案

“我会把流式 UI 拆成四步：先从连接里读字节，再按 SSE 协议拼成完整事件，接着把事件变成消息状态，最后才更新界面。这样半条事件不会被当成 JSON，旧会话的回复也有明确归属。完成和错误必须排在已收到的正文之后；渲染过密时再按帧合并更新。”

## 7. 幂等、并发和 AI 额度

### 面试问题

如果用户重复点击生成，或者网络超时后自动重试，如何避免重复生成和重复扣费？

### 项目版答案

**口述：**“单靠按钮防重复是不够的，网络重试也可能再发一次。我在后端给重要写请求加幂等键：同一个请求重来可以拿到原结果，参数变了就报冲突。生成任务和额度账本再各自做一次状态检查，只有还没结算的预占记录能进入终态。这样把重复请求和重复扣费分别拦住。”

**技术展开：**

项目通过多层机制处理：

1. 重要写接口要求 `Idempotency-Key`；
2. 服务端先用数据库唯一约束抢占 `PROCESSING` 记录；
3. 请求 Body 会生成稳定 fingerprint，同一个 Key 换参数会返回冲突；
4. 成功响应会持久化，后续相同请求可以回放；
5. AI 额度先进入 `reserved`，执行结束后只允许 `PENDING` 预占记录被结算一次；
6. 账户余额使用数据库原子增减，避免旧快照覆盖并发更新；
7. Worker 重试和任务恢复会先检查任务状态；
8. 失败和过期任务释放额度或执行补偿。

因此，重试不会简单地重复执行 Controller、重复创建任务或重复结算额度。

相关文件：

- [apps/server/src/common/idempotency/idempotency.interceptor.ts](../apps/server/src/common/idempotency/idempotency.interceptor.ts)
- [apps/server/src/common/idempotency/idempotency.repository.ts](../apps/server/src/common/idempotency/idempotency.repository.ts)
- [apps/server/src/modules/ai/ai-quota.service.ts](../apps/server/src/modules/ai/ai-quota.service.ts)
- [apps/server/test/idempotency.interceptor.spec.ts](../apps/server/test/idempotency.interceptor.spec.ts)

### 通用版答案

“防重复要分层。请求层用幂等键识别同一次提交；任务层用唯一业务号和状态约束防止重复执行；账务层用唯一流水和条件更新防止重复结算。前端按钮禁用只是减少误操作，网络重试、多个标签页或直接调用接口仍会到后端。”

## 8. 私密内容和 AI 引用权限

### 面试问题

项目如何实现私密内容？如何避免 AI 引用绕过内容权限？

### 项目版答案

**口述：**“私密内容不能只在详情页拦。列表、章节、收藏，甚至 AI 引用都要走同一套访问判断。我的规则是作者和指定读者能看，其他人在公开入口里连这条资源是否存在都不该知道。授权名单和公开状态可能被同时修改，所以我在数据库里按同一条内容记录串行处理这类变更。”

**技术展开：**

内容可见性有 `PUBLIC`、`LOGIN` 和 `PRIVATE` 三种状态。PRIVATE 内容支持作者本人和指定读者访问，未授权用户在公开路径按不存在处理，避免泄露标题、摘要和资源是否存在。

同一套可见性规则会应用到：

- 内容列表；
- 内容详情；
- 小册章节；
- 收藏和阅读进度；
- AI 知识内容引用。

AI 服务不会因为用户能提交一个 contentId 就直接注入内容，而是重新校验发布状态、作者/授权关系和版权闸。授权名单替换时对内容主行加锁，避免公开状态修改和授权更新产生不一致。

### 通用版答案

“资源访问规则要放在服务端，并让列表、搜索、详情、下载和 AI 引用等入口共用。只拦详情页，列表或引用接口仍可能泄露标题和摘要。对不该知道资源存在的人，可以按不存在返回；对明确有权知道资源但无权操作的人，再给权限错误。”

## 9. Outbox 和 BullMQ 的作用

### 面试问题

为什么不在 Controller 里直接调用 BullMQ？为什么还要 Outbox？

### 项目版答案

**口述：**“假如先写数据库、再直接发队列，数据库成功而队列失败时，任务就可能丢。我的做法是在同一个数据库事务里写业务记录和一条待发送事件，之后由 dispatcher 投递给 BullMQ，失败还能重试。BullMQ 负责排队和执行，Outbox 保证这件事最终有机会送到队列；Worker 仍要能处理重复消息。”

**技术展开：**

如果 Controller 先写数据库，再直接投递队列，可能出现数据库已经提交但队列投递失败，导致任务永远没人处理。

项目把业务数据和 Outbox 事件放进同一个数据库事务。事务成功后，`OutboxDispatcher` 定期读取 pending 事件并投递到 BullMQ；投递成功才标记为 dispatched，失败则记录错误并等待重试。

BullMQ 负责排队、重试、退避和 Worker 消费，Outbox 负责解决数据库状态和消息投递之间的一致性。

### 通用版答案

“数据库写成功、队列投递失败时，直接发消息会留下没人处理的任务。Outbox 把待投递记录和业务数据写在同一事务里，后续再可靠地送到队列；BullMQ 负责排队、重试和交给 Worker 执行。消息可能重复投递，所以 Worker 仍要按任务状态做幂等处理。”

## 10. 管理后台和权限菜单

### 面试问题

后台管理端有哪些功能？菜单权限如何实现？

### 项目版答案

**口述：**“后台主要做用户、角色、内容和系统配置管理。菜单由服务端按角色权限过滤，前端再映射到具体页面；即使菜单没显示，接口仍会做权限检查。另外，两个管理员同时改同一份角色权限时，我用版本号发现冲突，避免后保存的人悄悄覆盖前一个人的修改。”

**技术展开：**

后台包含用户、角色、权限、内容、内容审核、文件、AI 配置、系统配置、导航和日志等模块。

菜单不是简单地写死在前端。后端根据角色权限快照过滤菜单树，前端的 route registry 负责把服务端 routeKey 映射到实际页面。没有权限的菜单不展示，但接口访问仍由后端 Guard 校验。

角色权限更新带有版本号。管理端保存时提交旧版本，后端发现版本不一致会返回冲突，避免两个后台标签页互相覆盖。

### 通用版答案

“后台权限至少分两层：能不能执行某个操作，以及能操作哪些数据。菜单和按钮可以按权限隐藏，但后端接口必须再校验。列表查询要真正带上数据范围，不能只在页面上把不该看的行藏起来；敏感字段还要单独控制返回。”

| Interceptor | Nest 请求前后的横切逻辑 | 幂等、响应信封、性能和请求处理 | 适合统一处理，不应隐藏关键业务规则 |
| DTO | Data Transfer Object，接口输入输出对象 | 登录、内容、文件和 AI 参数校验 | DTO 是边界契约，不等于数据库实体 |
| JWT | JSON Web Token，带签名的身份令牌 | Access Token 携带用户和会话版本 | JWT 不是加密数据，不能放敏感信息 |
| Refresh Token | 用来换取新 Access Token 的长期凭证 | HttpOnly Cookie 续期和会话轮换 | 数据库只保存 Hash，旧 Token 重放会撤销会话 |
| HttpOnly Cookie | JavaScript 无法读取的 Cookie | 保存 Refresh Token，降低 XSS 直接窃取风险 | 还要配置 Secure、SameSite、Path 和 CORS |
| RBAC | Role-Based Access Control，基于角色的访问控制 | 角色映射权限码，并支持 `OWN/ALL` 数据范围 | 前端显隐不能替代后端校验 |
| Permission Guard | 权限守卫 | 根据服务端权限快照校验操作 | 不信任客户端权限列表 |
| Prisma | TypeScript/Node.js ORM 和数据库访问工具 | PostgreSQL 查询、事务和类型生成 | ORM 方便开发，但仍要理解 SQL、索引和事务 |
| PostgreSQL | 关系型数据库 | 用户、内容、权限、会话、额度和任务持久化 | 适合关系、事务、约束和复杂查询 |
| Redis | 内存型键值数据库 | 会话缓存、限流、验证码和 BullMQ 底座 | 适合临时状态，核心业务仍以 PostgreSQL 为准 |
| 限流 | 限制单位时间内的请求数量 | 登录失败、验证码和 AI 匿名调用保护 | 通常按用户、账号、IP 或组合键计数 |
| API | Application Programming Interface，应用程序接口 | 前端通过 REST 接口调用 Nest | API 应保持语义独立，不能绑定某个页面结构 |
| REST | 以资源和 HTTP 方法表达接口语义 | `/contents`、`/uploads`、`/auth` 等接口 | 重点是资源、状态码、幂等性和错误契约 |
| SSE | Server-Sent Events，服务端事件流 | AI 对话向浏览器持续推送增量文本 | 单向推送，适合文本流；事件边界不能等同网络 chunk |
| Provider | 对外部能力的适配接口 | Fake Provider 和 OpenAI-compatible Provider | 用依赖注入替换模型厂商，降低业务耦合 |
| OpenAI-compatible | 遵循 OpenAI 风格请求/响应协议 | 文本模型通过统一 `/chat/completions` 适配 | 兼容协议不代表所有模型能力完全相同 |
| Token | AI 模型处理文本的计量单位 | 输入/输出 token 用于 AI usage 和额度结算 | token 不等于字符数，项目有估算和 usage 回退策略 |
| 额度预占 | 先临时冻结可能消耗的资源 | AI 请求开始时从 available 转到 reserved | 防止并发请求同时通过余额检查 |
| 额度结算 | 按实际消耗确认最终扣费 | SSE 完成或媒体任务结束时 settle | 状态条件更新保证只结算一次 |
| BullMQ | 基于 Redis 的 Node.js 任务队列库 | 小册导入和图片/视频生成任务 | 支持延迟、重试、退避和 Worker |
| Worker | 独立消费异步任务的进程 | `server-worker` 处理 BullMQ 任务 | 与 Web HTTP 进程分离，避免阻塞请求 |
| Outbox | 事务内保存待投递事件的表或模式 | 数据库事务成功后由 dispatcher 投递队列 | 解决数据库提交成功但消息投递失败的问题 |
| Idempotency-Key | 标识同一业务请求的请求头 | 防止重复提交、重复创建任务和重复扣费 | 同 Key 不同 Body 返回冲突 |
| Fingerprint | 请求内容的稳定摘要 | 对请求 Body 排序后计算 SHA-256 | 用来判断重试是不是同一个业务请求 |
| 预签名 URL | 对象存储临时授权地址 | 浏览器直传文件和生成结果下载 | 应设置短过期时间，并在服务端控制生成条件 |
| Multipart Upload | 对象存储分片上传 | 大于 20MiB 的文件上传 | 分片有 ETag，complete 时合并并校验 |
| 文件魔数 | 文件开头用于识别类型的字节 | 防止伪造扩展名和 MIME | 只能作为类型校验的一部分，还要限制用途和大小 |
| SHA-256 | 密码学哈希算法 | 对上传对象流式计算完整性摘要 | 不能反推原文件，适合完整性和去重辅助 |
| CORS | 跨域资源共享策略 | `:8000`、`:8001` 访问 `:3001` API | Origin 白名单和 Cookie 配置必须一致 |
| Origin | 协议、域名和端口组成的来源 | 用户端和管理端各有一个 Origin | 端口不同也属于不同 Origin |
| HTTP 代理 | 转发浏览器请求到后端服务 | Umi dev proxy 将 `/api/v1` 转给 Nest | 要保留正确的 Origin/Referer，避免来源校验失败 |
| Docker Compose | 用配置编排多个容器服务 | Nginx、Web、Nest、Worker、PostgreSQL、Redis | 适合本地和首版生产的多服务启动 |
| Cursor / Codex | AI 编程工具 | 作为 PersonalHub 和 YGG 开发中的主要 Agent 工具 | 说明 AI 参与方案、编码、自查，自己负责取舍与验收 |
| Rules | 给 AI Agent 的仓库约束 | 限制生成范围、目录和工作流程 | 规则能降低偏离，不能替代代码审查与验收 |
| Skills | 可复用的 Agent 工作流程说明 | 固化提交、影响面分析等重复流程 | 与运行时业务代码不同，重点是让任务步骤一致、可检查 |

### 12.4 YGG 亿格 AI 平台：流式对话与媒体任务

**问：一分钟介绍项目和你的职责？**

**简历版回答：**“这是追觅汽车 IT 部门的 AI 平台，我负责前端开发。技术栈是 Vite、Vue 3 和 Element-Plus-X，功能包括 AI 对话、生图、生视频、历史会话、进度追踪、预览和下载。AI Agent 是主要开发工具，参与前端方案、编码和自查；交互取舍、接口联调和验收由我主导。前端重点是流式对话和媒体任务的状态处理。”

**通用参考答案：**“AI 平台的前端通常有两类流程：对话要边接收边展示，图片和视频则要跟踪长任务。我会先讲清用户操作，再讲前端负责的状态、接口联调和异常处理；结果只给有记录的指标。”

**问：`fetch` 读 SSE，如何处理并发、停止和断连？**

**简历版回答：**“对话不是等完整回答回来再显示。我用 `fetch` 读取 SSE 并流式渲染，同时支持多路对话和停止生成。并发时要让每条流对应自己的会话；连接中断和重复请求也要能让用户看清当前状态。这部分我负责前端实现和接口联调。”

**通用参考答案：**“读 SSE 时先缓存字节，遇到事件分隔符才解析，因为一次 `read()` 可能只拿到半条事件。并发请求各自保存会话 ID 和取消控制器；停止或断线后先查任务状态，不能直接重发生成请求。有事件 ID 或幂等协议时，才谈自动续传。”

**核实边界：** 简历未写请求 ID、服务端幂等策略或断点恢复协议；这些要结合当时实现再补细节。

**问：生图和生视频为什么统一成任务流程？**

**简历版回答：**“这两类生成的参数不同，但用户操作过程很像：配置参数、提交、等状态、预览和下载。我把前端任务流程统一起来，状态包括等待中、生成中、成功和失败；历史任务也能回显和复用结果。这样子页展示可以不同，状态和结果处理不用各写一套。”

**通用参考答案：**“生图、生视频都要经历提交、等待、执行和出结果，前端可以复用一套任务状态机，差异留在参数和结果展示。接口先返回任务 ID，页面再轮询或订阅状态；成功、失败和取消进入终态后要停止轮询。历史页从服务端任务记录恢复，不能只靠当前页面的内存。”

**追问准备：** Vue 3 组件边界可以从对话气泡、输入框、会话列表和媒体页讲起；子页状态缓存要能说明缓存了什么、何时失效。简历没有给出并发上限、轮询间隔或性能数字，准备本人真实经历后再补。

### 12.5 追觅汽车官网：接手主题、多语言与首屏

**通用参考答案：**“三图轮播的核心是只维护一个当前索引，主图和两侧图片的位置都由它计算，切换动画才不会错位。首尾衔接、不同图片宽高和移动端触控要单独验证；如果要无缝循环，可以用克隆节点或动画结束后重置位置。”

**简历版回答：**“我在主题编辑器加了多语言切换，在主题代码补语言判断，解决部分页面切换后又回中文的问题。首屏上，用体积较小的 MiSans WOFF 替换原来的全量字体，把几个较大的 JS 改为后置加载。”

**通用参考答案：**“多语言不能只换按钮文案，路由、模板内容和语言持久化也得用同一个语言状态。首屏慢时先看哪些字体和脚本挡住了展示，再决定拆字体、延迟脚本或调整加载顺序。优化前后要在同样设备和网络条件下比资源体积与 LCP。”

**核实边界：** 简历没有首屏耗时或资源体积的前后对比数字。

**问：一分钟介绍项目和你负责的部分？**

**简历版回答：**“这条业务线一边是农行 App 里的热门活动、搜索和礼券，一边是运营后台的活动发布、审核、报表、权益和公域引流。我负责搜索与热门活动的 Hybrid 页面，做过跨 App 跳转和客户信息获取；后台方面封装过配置化 form/table，并基于它们开发活动列表、活动页、报表、公域引流和部分权益功能。”

**通用参考答案：**“Hybrid 活动页是在 App 的 WebView 里跑的，页面负责展示和交互，跳转、身份等能力要通过客户端桥接。介绍这类项目时，我会把 App 页面、桥接接口和运营后台分开讲，说明每一部分的职责和联调边界。”

**问：AlipayJSAPI、RPC 封装和鸿蒙适配有什么难点？**

**简历版回答：**“我基于 AlipayJSAPI 做跨 App 跳转和客户信息获取，又把活动、搜索和埋点等 Hybrid 接口调用收进统一的 RPC 请求函数，减少重复请求。页面还要按设计稿适配不同屏幕和鸿蒙环境。难点在于这些页面运行在 App 容器里，页面与客户端能力要一起联调。”

**通用参考答案：**“Bridge 调用前先确认当前容器支持这个能力，调用后要分别处理成功、拒绝、超时和客户端版本不支持。统一 RPC 封装可以收拢参数、错误和埋点，但页面仍要知道哪些操作失败后能重试、哪些不能。鸿蒙适配要同时看布局和 WebView/桥接行为。”

**核实边界：** 具体容器版本、授权失败处理和返回栈问题需要按本人真实案例补充。

**问：JSON 配置化 form/table 如何避免越抽越复杂？**

**简历版回答：**“当时用 Element-UI 做通用 form/table，页面用 JSON 描述字段和列。form 支持自定义项、插槽、栅格和校验；table 支持单选、全选、展开列和分页。我的取舍是把重复的展示与交互配置化，特殊业务仍留扩展点，避免所有页面都去改公共组件。”

**通用参考答案：**“配置化表单适合字段和布局规律比较稳定的后台页面，schema 负责常见字段、校验和列配置，特殊交互交给插槽。若一个页面为了适配公共组件要写很多条件分支，说明抽象已经过头，应让它用业务组件组合。”

### 12.7 超级表格平台：协同富文本与保存链路

**问：一分钟介绍项目，为什么换富文本方案？**

**简历版回答：**“这是农行内部协同办公平台，包含表格、收集表、流程图和在线文档等模块。我主要能展开富文本协同这条线：原来 Quill 偏个人编辑，实时协同能力不满足需求；CKEditor 改源码方案推进受阻后，选了 Textbus 加 Yjs。我用 Textbus API 重写有序列表和图片上传，也做了目录、保存和历史版本。”

**通用参考答案：**“选协同编辑方案时，我会先看编辑器的数据模型能否和协同库配合，再看扩展功能、旧数据迁移和维护成本。CRDT 解决多人改同一份文档时的合并问题；权限、落盘和历史恢复还得另外设计。”

**问：协同通信和保存链路是怎样的？**

**简历版回答：**“我用 Express 做 Node 中间件，y-websocket 负责协作通信，结合 y-redis 将文档写到 Redis，再同步到 ufile。用户可以手动保存，也支持断线自动保存、历史版本查看和还原。这个链路里，实时同步与持久化要分开看：编辑时看到一致，不代表版本已经安全落盘。”

**通用参考答案：**“协同编辑有三个状态：我本地改了什么、服务器同步了什么、哪一版已经持久化。看到别人的修改不等于保存成功，所以界面应提示保存状态并允许失败重试。断线重连要补齐更新；恢复旧版本还要处理正在编辑的人和权限。”

**问：图片、甘特图和收集表分别做了什么？**

**简历版回答：**“图片不再直接把 base64 写进文档，而是上传后使用 ufile 链接，也支持点击放大。多维表格方面，我读过 x-data-spreadsheet 源码，参与后期开发并处理甘特图相关问题；还和后端配合做过收集表数据转换、封装权限审批弹窗。”

**通用参考答案：**“把图片上传成文件链接，比把 base64 塞进正文更容易控制文档体积，但要管好链接权限和失效。甘特图要把任务日期映射到时间轴；收集表数据转换则要把字段类型、空值和权限规则先定清楚，再举一条输入输出说明结果。”

### 12.8 移动报告应用与后台管理系统：简历中的早期经历

**问：这段经历主要做过什么？**

**简历版回答：**“在华晨宝马驻场阶段，我做过移动报告应用的多机型适配、拍照和录像上传重试，也参与过后台管理系统的 ECharts 配置化，以及 PPT、Excel 导出。这段经历主要锻炼了我处理不同设备上的上传体验，以及把报表展示和导出做成可复用流程的能力。”

**通用参考答案：**“移动端拍照或录像上传要区分选文件、传输和服务端确认，失败重试不能让同一文件出现多份。报表方面，图表配置负责把业务字段映射到展示方式；导出时还要处理数据量、文件格式和生成失败后的反馈。”

**追问准备：** 上传重试可以按“哪一步失败、用户如何继续、怎样避免重复上传”准备真实例子；报表导出按“选数据、生成文件、下载”准备输入输出。PDF 只用一行概述了这两项，具体协议、库和性能数字需要本人补充，不要套用 PersonalHub 的上传链路。

## 13. React 和前端项目专项面试题

本节保留 PersonalHub 的项目版答案。React 通用原理和源码题统一见 [前端基础与框架原理面试问答](./frontend-fundamentals-interview-qa.md)。

### 13.1 React 项目如何组织页面和组件？

**口述：**“我按页面、业务组件和通用组件来拆。比如 AI 工作台的外框只管布局，输入组件只管交互，会话和流式状态放在 Hook 里。这样换一个 AI 工具时可以复用输入区，不会把聊天的状态一起带过去。”

**技术细节：** 项目按应用、页面、领域组件和共享组件分层。公开内容、工作区、AI 和管理后台分别有自己的页面入口；AI 内部再按布局、输入区、消息气泡、历史列表和 Hook 拆分。`AiWorkspaceFrame` 只负责布局，`AiComposer` 负责输入交互，`useAiChat` 负责会话和流式状态。这样结构复用和业务状态没有混在一起。

### 13.2 `useState`、`useEffect` 和 `useRef` 分别怎么用？

**口述：**“需要影响界面的输入和加载状态放 useState；请求、订阅这种要和外部系统同步的逻辑放 useEffect，并在退出时清理；当前请求 ID 和表格引用这类跨渲染要保存、但不用触发界面更新的值放 useRef。”

**技术细节：** `useState` 管理输入、加载、弹窗和筛选等会影响 UI 的状态；`useEffect` 用于启动请求、主题同步、监听变化和清理副作用；`useRef` 保存当前 SSE 请求、ProTable actionRef 或不需要触发渲染的最新值。AI 场景中尤其要把请求身份放在 ref 中，防止旧请求回写当前会话。

### 13.3 React 中如何避免异步请求竞态？

**口述：**“我会同时做两件事：尽量取消旧请求，并在结果回来时确认它还属于当前页面。AI 对话更特殊，切换会话并不取消旧流，旧流继续写到原来的会话；只有页面卸载才清理这些流。”

**技术细节：** 项目在内容授权抽屉和 AI 对话中使用加载序号、当前 ID 和 AbortController：切换内容时先清理旧表单，旧请求返回时检查序号；切换会话只切换视图，旧流继续写入原会话快照；当前页面最多允许三条会话同时生成，建会话等待也占名额。历史请求通过会话修订号丢弃过期快照，页面卸载时才清理全部流。首次会话从占位 ID 绑定真实 ID 时保留当前请求和消息。

### 13.4 `useMemo` 和 `useCallback` 应该什么时候使用？

**口述：**“我不会默认给每个值都套 memo。只有派生数据计算比较重，或者传给子组件的引用变化确实造成重复渲染时才加；加完还要看依赖是否正确和实际收益。”

**技术细节：** 项目在派生菜单、筛选选项和配置数据需要稳定结果时使用 `useMemo`，在模型配置、主题和筛选操作需要稳定回调时使用 `useCallback`。它们不是默认优化手段，只有计算成本、依赖引用或子组件 memo 确实存在收益时才使用。

### 13.5 如何理解受控组件和非受控组件？

**口述：**“表单字段通常由 React 或表单实例管理，这样校验、回填和保存比较方便。文件内容我不会整个塞进 state，只保留文件对象、进度和必要元数据。”

**技术细节：** AI 输入、内容编辑草稿、主题配置和后台表单主要使用受控方式，值由 React 或表单实例统一管理，便于校验、回填、撤销和保存。文件上传等场景会同时使用浏览器 File 对象和上传任务状态，文件内容本身不复制进 React state，只保存必要的元数据和状态。

### 13.6 Umi 的 `useRequest` 为什么要二次封装？

**口述：**“项目的请求拦截器已经把后端响应解包了，页面拿到的是业务对象。Umi 的 useRequest 默认还会再取一次 data，所以我在统一 Hook 里改了结果格式，避免每个页面都写特殊处理。”

**技术细节：** Umi 的 `useRequest` 默认会按 `result.data` 取值，但项目的全局请求拦截器已经把 Nest 信封解包成业务对象 `T`。如果直接使用默认行为，页面会再次读取 `data`，导致真正的数据变成 undefined。因此项目在 `apps/*/src/hooks/useRequest.ts` 中覆盖 `formatResult`，保持页面拿到 `T`。

### 13.7 React 页面如何处理 loading、empty、error 三种状态？

**口述：**“我会把‘还在加载’‘成功但没有数据’‘请求失败’‘没有权限’分开。比如列表为空要给创建入口，失败要给重试，403 要明确告诉用户无权访问，不能统一显示一个空白页。”

**技术细节：** 项目使用 PageLoading、SectionSkeleton、EmptyState、ErrorState、ForbiddenState 和 ResultState 等共享状态组件。请求未完成时不直接渲染空白，数据为空时给出明确空态，请求失败时提供重试或返回入口，权限不足时使用 403 状态。公开系统配置失败时还会保留默认配置，不让整个首页无法打开。

### 13.8 为什么要使用 React.lazy 和代码分割？

**口述：**“PDF 和图表只在少数页面用，放在首屏包里会让所有人付出下载成本。我把它们放到打开对应功能时再加载，并为等待和加载失败准备界面。”

**技术细节：** PDF、图表库、设置抽屉和部分页面不是所有用户首次打开都需要，所以项目把它们拆到异步包中。`/status` 的图表只在需要时加载，PDF 预览只在打开时加载，避免这些大依赖进入首页入口包。

### 13.9 Error Boundary 能捕获哪些错误？

**口述：**“Error Boundary 主要兜住子组件渲染阶段的错误。接口报错、点击事件里的异常和异步回调并不会自动被它捕获，所以请求层和页面仍要有自己的错误处理。”

**技术细节：** 项目使用 ErrorBoundary 兜底渲染错误和懒加载组件失败，并提供重试机制。它不能替代请求错误处理，所以接口失败仍由 Umi request errorHandler、页面 error state 和后端错误码处理。

### 13.10 如何设计一个可复用的 AI 输入框？

**口述：**“我先把输入、模型选择、发送和停止这些共性交互做成一个组件。聊天会话、图片任务等业务状态由各自页面管理，通过值和回调传给组件；这样复用的是交互，不是把所有业务塞到一起。”

**技术细节：** `AiComposer` 统一处理输入框、模型选择、配置摘要、附件、发送、停止和更多操作，但不直接持有具体页面的会话或生成任务状态。Chat、Image、Video 通过 props 传入当前模式和回调，具体状态仍由页面或 Hook 管理。手机端按钮放不下时，配置和低频操作收进更多菜单。

### 13.11 ProTable 和普通 Table 怎么选？

**口述：**“后台列表如果有分页、筛选、工具栏和刷新，我会用 ProTable，省掉很多重复状态。展示型或交互特别定制的表格，我会用普通 Table 或自己的组件。”

**技术细节：** 管理后台的用户、角色、内容审核、文件和日志使用 ProTable，因为这些页面需要分页、筛选、工具栏、刷新和操作列。简单的静态展示或自定义消息流不使用 ProTable，而使用普通组件和页面自己的状态。

### 13.12 React 页面如何做性能优化？

**口述：**“我先看是加载慢、交互卡还是接口慢，再分别处理。项目里 PDF 和图表做按需加载，AI 增量按帧更新，性能面板记录页面和接口指标。没有同口径数据时，我不会报一个‘提升了多少’。”

**技术细节：** 项目从三个层面做优化：入口层通过懒加载把 PDF、图表和设置抽屉移出首屏；渲染层通过 AI 分帧调度器减少高频状态更新；观测层采集 Web Vitals、路由耗时和接口 p95，在 `/status` 展示。优化前后通过入口包大小和性能面板对比，而不是只凭感觉。

### 13.13 React 响应式布局为什么还需要 JavaScript？

**口述：**“CSS 可以让东西变窄，但手机上有些交互要换形态：导航改抽屉，阅读操作改底栏，放不下的 AI 按钮收进更多菜单。这种组件结构变化需要 React 配合视口状态。”

**技术细节：** CSS 负责尺寸和排列，但交互结构需要 React 判断。例如手机端导航改成 Drawer、阅读器改成底部操作栏、Chat 会话历史移入 Drawer、AI 输入按钮放入更多菜单。这些不是单纯改变 CSS 就能完成的结构变化。视口档位来自统一的 `viewport-bands.json`，避免 JS/CSS 断点不一致。

### 13.14 React 中如何处理主题切换？

**口述：**“主题有三层来源：代码默认值、站点配置、用户自己的偏好。启动时按这个优先级合成，再同步到 CSS 变量和组件主题，避免页面和弹窗颜色不一致。”

**技术细节：** 项目把站点主题配置、用户本地主题偏好和运行时 CSS 变量结合：启动时拉取公开配置，读取本地偏好覆盖明暗和主色，ThemeProvider/ThemeRuntimeSync 订阅变化并同步到页面。优先级是用户本地偏好高于站点配置，高于代码默认值。

### 13.15 React 前端如何处理权限？

**口述：**“前端会按权限隐藏菜单和按钮，让用户少碰到不可用操作。但这只是体验层，后端每次仍要验证操作权限、数据范围和资源归属。”

**技术细节：** 前端通过 initialState、权限快照和 route registry 过滤菜单、控制路由入口和按钮显隐；`PermissionGate` 提供局部 UI 兜底。但真正的权限在 Nest `PermissionsGuard` 和资源归属检查中完成，前端隐藏按钮不当作安全方案。

### 13.16 为什么不能把所有数据都放进 React 全局状态？

**口述：**“我按数据的生命周期放状态：输入和弹窗留在组件里，当前用户和主题放应用层，列表和历史记录按服务端数据处理，阅读偏好放本地。全部扔进全局状态，会让刷新和错误处理变得混乱。”

**技术细节：** 项目把状态按生命周期拆开：输入框和弹窗属于组件本地状态；主题、当前用户和菜单属于应用启动状态；内容列表、AI 历史和任务属于服务端状态；阅读偏好属于 localStorage。这样可以避免全局状态过大、刷新策略混乱和不同页面互相污染。

### 13.17 如何回答“React 和 Vue 的区别？”

**口述：**“我做过 Vue 和 React 项目。Vue 的响应式和模板写法更集中，React 更强调用 JavaScript 组合组件；在这个项目里选 React/Umi，主要看中 Ant Design Pro 的后台生态。面试时我更愿意结合实际场景讲取舍，而不是说哪个框架绝对更好。”

**技术细节：** 我的项目同时有 Vue 和 React 经验。PersonalHub 选择 React/Umi/Ant Design Pro，是因为需要快速搭建用户端和管理端，并且 Ant Design Pro 对中后台布局、表格和表单有成熟约定。YGG 项目使用 Vue3/Element-Plus-X，核心差异体现在组件模型、响应式机制和生态约定，但业务上都要解决状态、请求、错误和性能问题。


## 14. 按主题聚合的深挖追问

这一节把面试官常见的连续追问集中起来。实际面试时，面试官通常会从一个关键词一路追到设计原因、失败场景和验证方式。

### 14.1 认证、Cookie、JWT 和 RBAC

**口述：**“Access Token 在页面内存里，Refresh Token 放 HttpOnly Cookie，数据库保存它的哈希。这样可以轮换和撤销会话。菜单隐藏只解决体验，接口仍会按权限和资源归属校验；OWN 范围还要真正落进查询条件。”

**可能的追问链：**

1. 为什么 Access Token 不放 localStorage？
2. Refresh Token 放在哪里？数据库保存什么？
3. Refresh Token 被盗或被重放怎么办？
4. 用户修改权限后，旧 JWT 里的权限如何失效？
5. 前端按钮隐藏后，接口还需要校验吗？
6. `OWN` 和 `ALL` 数据范围如何落到查询？

**逐问速答：**

1. Access Token 放内存，页面关闭后自然消失；放在 localStorage 会延长被脚本读取的机会，但仍要防 XSS。
2. Refresh Token 在 HttpOnly Cookie；数据库保存带 pepper 的哈希，不保存明文。
3. 刷新时轮换 Token；旧 Token 再出现时撤销该会话，并要求重新登录。
4. JWT 带版本号，后端按版本读取当前权限快照；角色变更不必等旧 JWT 到期。
5. 需要。按钮隐藏只改善界面，接口仍检查操作权限、数据范围和资源归属。
6. `OWN` 把当前用户的归属条件写进查询，`ALL` 允许更广范围但仍须有操作权限。

**技术展开：** 项目把短期 Access JWT 放在当前页面内存，Refresh Token 放 HttpOnly Cookie，数据库只保存带 pepper 的 Hash。刷新时轮换旧 Token，旧 Token 再出现则撤销当前会话。JWT 只携带 `authVersion` 和 `permissionVersion` 等必要信息，权限从服务端快照读取，所以角色变化不依赖等待 JWT 自然过期。前端只负责菜单和按钮体验，后端 Guard 重新校验权限码、数据范围和资源归属。

**追问展开：** 内存存储减少 Token 在持久存储中被窃取的窗口，但不能阻止正在运行的 XSS 代用户操作；HttpOnly 也不能替代 CSRF 防护。`OWN` 要在查询条件中加入当前用户归属约束，`ALL` 也必须先通过对应操作权限检查；详情接口同样验证资源访问范围，不能只过滤列表。

### 14.2 数据库、事务和并发

**口述：**“跨进程的并发我放到数据库里处理。改角色权限用版本号发现覆盖；任务和额度用条件更新只允许一个请求进入终态；内容授权修改会锁住同一条内容记录。事务范围尽量短，避免锁等待。”

**可能的追问链：**

1. 哪些操作必须开启事务？
2. 两个请求同时修改角色权限怎么办？
3. 两个请求同时授权或公开同一篇内容怎么办？
4. 为什么不用进程内锁？
5. 如何避免旧查询结果覆盖新数据？
6. 哪些地方使用条件更新，哪些地方使用行锁？

**逐问速答：**

1. 会话创建、额度预占、授权替换和上传完成等需要把多项数据库变更一起提交。
2. 提交时检查角色版本；版本已变就返回冲突，让操作者重新读取后再改。
3. 授权和公开状态修改都锁住同一条内容主记录，按数据库顺序处理。
4. 服务和 Worker 可能运行在不同进程，进程内锁管不到另一进程。
5. 前端按请求身份或加载序号验收结果；后端写入还要检查版本或状态。
6. 抢任务终态、额度结算用条件更新；替换授权名单这类多步操作用事务和内容行锁。

**技术展开：** 登录创建会话和 Refresh Token、额度预占、内容授权替换、上传完成状态和 Outbox 事件需要事务。角色权限保存带版本号，旧版本提交会返回冲突；额度和任务状态用 `PENDING` 条件更新抢占终态；内容授权替换会锁住内容主行，保证授权变化和公开状态修改按数据库顺序提交。锁和条件更新放在数据库层，因为服务可能有多个进程或 Worker，进程内锁无法覆盖跨进程并发。

**继续追问：锁是否会死锁？** 有可能。应固定资源加锁顺序、缩短事务，并对数据库可重试错误设置有界重试。项目用数据库主行锁与条件更新处理特定并发，不能声称已经覆盖所有死锁场景。

### 14.3 幂等、重试和失败恢复

**口述：**“同一个幂等键、同一份参数重来时，先等待正在处理的请求，完成后回放结果；参数变了直接报冲突。进程中途挂掉还要靠超时和心跳恢复，任务与扣费又分别有状态保护。”

**可能的追问链：**

1. 用户重复点击会不会创建两条任务？
2. 网络超时后客户端重试怎么办？
3. 为什么不能先查询幂等记录再插入？
4. 第一个请求执行期间第二个请求如何处理？
5. 第一个请求进程崩溃后 `PROCESSING` 如何恢复？
6. 同一个幂等键换了请求体怎么办？

**逐问速答：**

1. 用户重复点击携带同一幂等键，服务端回放同一结果；前端禁用按钮只是辅助。
2. 先查原操作状态，再用原幂等键重试，避免把“没收到响应”当作“没写成功”。
3. 先查再插存在并发空档；唯一约束下的原子 claim 才能让一个请求先占位。
4. 参数相同的后来请求等待已占位请求，完成后回放结果；久等无结果则返回冲突。
5. 长任务刷新心跳，超时的旧占位可被重新声明；业务状态仍要保证可重入。
6. 对比请求指纹，参数变了直接返回冲突，不能把新操作伪装成原操作。

**技术展开：** 重要写接口要求 `Idempotency-Key`，服务端利用唯一约束先原子 claim `PROCESSING`，再执行业务。相同 Key 和 fingerprint 的请求等待或回放结果，不同 Body 返回冲突。长耗时操作定期刷新心跳，超过 stale 时间可以被重新声明；业务失败释放 claim，避免错误占位。任务层再用 jobId 和状态机保证 Worker 重试可重入，账务层用预占记录的条件更新保证只结算一次。

### 14.4 AI SSE、额度和异步媒体任务

**口述：**“文本用 SSE，是为了让用户马上看到回复；图片和视频用队列，是因为生成时间不可控。前端先拼完整事件再按帧渲染，后端先预占额度，成功结算、失败释放。重复消费不能重复扣本地账，但外部厂商是否重复收费还要另做幂等或对账。”

**可能的追问链：**

1. 为什么文本对话用 SSE，图片/视频用队列？
2. 网络 chunk 为什么不能直接 JSON.parse？
3. 用户点击停止后，已经收到但还没渲染的文本怎么办？
4. AI 额度如何预占和结算？
5. 上游模型超时或返回损坏数据怎么办？
6. Worker 重启或重复消费会不会重复扣费？

**逐问速答：**

1. 文本需要边生成边显示，适合 SSE；媒体生成耗时不可控，交给队列和状态查询。
2. 一个网络 chunk 可能只有半条事件，必须等到 SSE 事件边界再解析。
3. 先把已收到但尚未显示的文本刷到页面，再调用停止接口；收到终态后结束本次流。
4. 请求开始预占额度，成功按实际用量结算，失败或过期释放。
5. 上游异常进入错误终态，释放或补偿额度；已收到的内容与错误状态分别处理。
6. 本地终态和账务条件更新防重复扣账；外部厂商仍需幂等能力或对账。

**技术展开：** 文本对话需要尽快反馈，使用 Nest 代理上游 SSE 并把增量转成 `STARTED/DELTA/DONE/ERROR`；前端按 SSE 空行边界组装事件，再通过 requestAnimationFrame 调度渲染。图片和视频耗时不可控，所以 API 只创建任务，Outbox 投递 BullMQ，Worker 更新状态并保存结果。AI 请求先预占额度，成功后按实际 usage 结算，失败或过期释放；终态和扣费都使用条件更新，重复消费只会命中已结束状态。

**继续追问：上游超时、损坏数据和停止怎么区分？** 解析失败或上游异常走错误终态与额度释放/补偿；显式停止应保留已生成内容，依业务终态结算。Worker 终态条件更新保护本地账务，但不能证明外部供应商只执行或收费一次；外部副作用还需要供应商幂等键或任务查询恢复。

### 14.5 文件上传、对象存储和 ZIP 安全

**口述：**“浏览器拿短期上传地址直接传对象存储，Nest 不扛文件流量。传完后后端再查大小和内容，计算并保存摘要；ZIP 还要限制路径和解压规模。上传地址如果泄露，在有效期内就可能被人使用，所以有效期和权限范围要控制好。”

**可能的追问链：**

1. 为什么浏览器直传对象存储？
2. 预签名 URL 被别人拿到怎么办？
3. 为什么不能只校验扩展名和 MIME？
4. 大文件为什么要 multipart？
5. SHA-256 为什么要流式计算？
6. ZIP 导入如何防路径穿越和 ZIP Bomb？
7. complete 接口调用两次怎么办？

**逐问速答：**

1. 浏览器直传，应用服务只签发凭证和验收，避免承受大文件流量。
2. URL 在有效期内相当于临时凭证；缩短有效期并限制方法、对象 key 和签发权限。
3. 扩展名和 MIME 都可伪造，完成上传后还要检查对象大小和文件魔数。
4. multipart 让大文件分段上传和重试；项目超过 20MiB 走这条路径。
5. 边读边算摘要，避免把整个文件放进内存；当前摘要用于记录指纹。
6. 拒绝 `..` 等越界路径，并限制条目数、展开大小和压缩比。
7. 用状态条件更新抢占完成动作；已 READY 的文件重复 complete 返回既有结果。

**技术展开：** Nest 只创建上传会话和预签名 URL，浏览器直传对象存储，避免应用服务承受大文件带宽和内存压力。服务端按用户、用途和文件策略限制上传，complete 时校验对象大小和魔数，并流式计算、保存 SHA-256 文件摘要；预签名 URL 有过期时间，下载还要重新检查文件归属。大于 20MiB 使用 multipart。ZIP 解析拒绝 `..` 路径、限制章节数、单章大小和压缩比；完成上传使用条件更新，所以重复 complete 只返回已经 READY 的文件。

**继续追问：预签名 URL 泄露后还能阻止访问吗？** URL 在有效期内通常是持有者可用的临时凭证。业务鉴权发生在签发前，不能假设对象存储每次使用 URL 都回调 Nest 鉴权。应缩短有效期、限制方法和对象 key，并避免泄露。当前 SHA-256 是计算后保存的指纹，没有与可信预期摘要比较，因此不能声称已做端到端摘要一致性验证。

### 14.6 Outbox、BullMQ、Worker 和部署

**口述：**“业务记录和待投递事件一起提交数据库，之后再把事件送到队列。这样队列暂时故障时还有记录可重试。Worker 也要检查任务状态，因为队列消息可能重复送达。”

**可能的追问链：**

1. 为什么不在 Controller 里直接发消息？
2. 数据库成功、队列失败怎么办？
3. Worker 挂掉后任务怎么办？
4. 消息重复投递怎么办？
5. Web 进程和 Worker 为什么分开？
6. 生产环境怎么启动这些服务？

**逐问速答：**

1. 直接发队列会遇到数据库回滚但消息已发、或数据提交后发消息失败的问题。
2. 业务记录和 Outbox 同事务提交，队列失败时 dispatcher 根据待投递记录重试。
3. BullMQ 可重试任务；Worker 再检查业务状态，避免重跑时重复写终态。
4. 允许消息重复到达，任务按 jobId 和状态机处理，账务再做条件更新。
5. 媒体生成与导入耗时长，独立 Worker 避免占住 HTTP 进程。
6. 当前用 Compose 启动 Nginx、静态前端、Nest server、server-worker、PostgreSQL 和 Redis。

**技术展开：** 业务数据和 Outbox 事件在同一数据库事务中写入，dispatcher 扫描 pending 事件并投递 BullMQ，成功后才标记 dispatched。这样数据库提交成功后，即使当时队列不可用，后续仍可重试。Worker 独立运行，避免导入和媒体生成阻塞 HTTP。任务处理按 jobId 和状态机幂等，生产使用 Compose 编排 Nginx、静态前端、Nest server、server-worker、PostgreSQL 和 Redis。

### 14.7 React 状态、请求竞态和组件设计

**口述：**“组件本地只管输入和弹窗，服务端数据按请求状态管理。请求回来时核对身份，避免旧结果写进新页面；AI 会话切换时旧流继续写原会话。公共输入组件复用交互，具体任务状态留在页面。”

**可能的追问链：**

1. 哪些状态放组件，哪些放全局？
2. 页面切换时旧请求会不会回写新页面？
3. 为什么 `useRequest` 需要覆盖 `formatResult`？
4. 公共组件如何避免和业务状态耦合？
5. loading、empty、error、forbidden 怎么区分？
6. 为什么 AI 输入框可以复用，业务状态却不能全放进去？

**逐问速答：**

1. 输入和弹窗留在组件，用户与菜单放共享状态，列表和任务按服务端请求管理。
2. 旧请求回来时核对请求身份或加载序号，不让它覆盖当前页面。
3. 全局请求层已把响应解成业务数据，自定义 `useRequest` 要避免再次取 `data`。
4. 组件只收值、状态和事件回调，不直接依赖某条业务 API。
5. loading 是等待、empty 是成功但无数据、error 是失败、forbidden 是无权访问。
6. 输入操作相似，适合复用；会话、任务与额度规则各异，交给页面或 Hook。

**技术展开：** 项目把输入框和弹窗放组件本地 state，把用户、主题和菜单放 initialState，把列表和任务当服务端状态，把阅读偏好放 localStorage。请求使用 requestId、加载序号和 AbortController 处理竞态；公共 AI 组件只负责结构、输入和按钮编排，页面或 Hook 持有会话、任务和请求状态。Umi 全局拦截器已经解包响应，所以项目自定义 `useRequest` 防止 Umi 默认再次取 `data`。

**追问展开：** loading 表示还未得到结果，empty 表示请求成功但集合为空，error 表示请求失败，forbidden 表示服务端拒绝访问；不能把失败统一转成空数组，否则用户会误以为数据不存在。共享输入框通过值与事件回调复用，页面负责鉴权、创建任务和错误恢复，避免组件直接依赖某条业务 API。

### 14.8 React 性能、加载和响应式

**口述：**“我先看实际是首屏加载慢还是流式渲染卡。PDF 和图表按需加载，AI 文本按帧提交；性能面板按固定口径看 Web Vitals 和接口耗时。某项没样本就不算进总分，全部没样本就显示数据不足。”

**可能的追问链：**

1. 如何证明懒加载有效？
2. 为什么 PDF 和图表库不放入口包？
3. AI 流式更新为什么会卡？
4. 为什么移动端响应式还要 JavaScript？
5. 没有性能样本时如何评分？
6. `useMemo` 和 `useCallback` 是否越多越好？

**逐问速答：**

1. 对比相同构建配置下的入口包和异步包，再看同口径页面指标。
2. PDF 和图表依赖较重，只在打开对应功能时加载。
3. 每个增量都触发 React 更新会增大渲染开销，所以按帧合并提交。
4. CSS 调布局；移动端 Drawer、底栏等结构变化需要 React 判断视口档位。
5. 缺失项不计入分母；全部缺样本返回“数据不足”，不硬给分。
6. 不是。先量计算和渲染成本，确定缓存收益大于维护成本再用。

**技术展开：** 项目把 PDF、图表和设置抽屉放到异步包，使用构建产物验证入口体积；AI 文本通过 requestAnimationFrame 限制 React 更新频率；性能面板采集 Web Vitals、接口 p95 和路由耗时。CSS 负责排列，React 根据视口档位改变 Drawer、底栏和更多菜单等结构。`useMemo/useCallback` 只在计算成本或引用稳定性有明确收益时使用。

**继续追问：没有性能样本时如何评分？** `score.ts` 中缺少的指标不计入加权分母，已有指标按剩余权重归一；全部缺失返回 `null`，界面显示数据不足。不能把缺样本记成 0 分或 100 分。完整页面加载的 Web Vitals 与 SPA 路由观测值也要区分口径。

## 15. 工程化落地类的额外追问

前面的章节覆盖了业务难点和 React 项目实践。面试官如果继续确认项目是否真正落地，常会从下面这些工程问题追问。它们不一定写在简历上，但能检验你是否理解从开发到上线的完整链路。

### 15.1 前后端如何保证 API 契约一致？

**口述：**“我把接口类型放在共享包里，调用统一走 api-client。后端的响应在请求入口解包，页面只处理业务数据；出错时统一抛给错误处理。这样改字段时编译能先发现一部分问题，关键路径还要靠接口测试确认。”

**技术细节：** 项目把共享 DTO、枚举和响应类型放在 `packages/shared-types`，前端通过 `packages/api-client` 访问接口。Nest 返回统一响应信封，Umi request 层在边界统一解包，页面拿到的是业务对象；错误统一抛出并由 request error 配置读取 `error.message`。这样页面不用重复判断 `code === 0`，接口字段变化也有共享类型和编译检查兜底。

**通用版答案：** API 契约应该明确请求、响应、错误、分页和版本策略，可以通过 OpenAPI、共享类型或代码生成减少手写偏差。统一处理放在请求边界，业务页面只消费稳定的业务数据，避免每个调用方各写一套解包和错误判断。

### 15.2 为什么要区分 liveness 和 readiness？

**口述：**“live 只回答‘进程还在不在’，ready 回答‘现在能不能接请求’。项目的 ready 会检查数据库、Redis 和对象存储，所以依赖故障时能看到是哪一项出了问题；生产入口的行为我会按当前 Compose 配置如实说明。”

**技术细节：** `live` 只确认 HTTP 进程能响应；`ready` 检查 PostgreSQL、Redis 和对象存储，任一关键依赖不可用时返回 `503`。当前生产 Compose 用 `ready` 判断 server 是否健康，并在首次启动 Nginx 前等待它健康；现有 Nginx 只有一个 Nest upstream，没有按探针结果动态摘除实例的配置。排查时可根据 `ready` 返回的依赖状态定位故障，不能说“Redis 故障后 Nginx 自动切到其他实例”。

**通用版答案：** liveness 解决“进程是否需要重启”，readiness 解决“当前实例是否可以接流量”。两者检查项和失败处理不同，不能用一个过重的健康接口代替全部探针。

### 15.3 项目如何设计测试策略？

**口述：**“我把测试重点放在出错代价高的地方：登录权限、重复请求、私密内容、额度和文件校验。前端用小测试覆盖 SSE 解析等纯逻辑，后端用真实 PostgreSQL 和 Redis 的集成测试确认事务与缓存行为。”

**技术细节：** 前端使用 Vitest 覆盖 SSE 解析、AI 传输、响应式断点和导航等纯逻辑；后端用 HTTP 集成测试覆盖认证、RBAC、幂等、内容可见性、文件校验和 AI 额度；Testcontainers 启动临时 PostgreSQL/Redis 验证 migration、readiness 和 Redis 故障。测试重点放在并发、异常和边界，而不是重复测试简单的 JSX 展示。

**通用版答案：** 单元测试验证纯函数和状态转换，集成测试验证数据库、缓存、队列和 HTTP 契约，端到端测试验证关键用户路径。测试优先覆盖高风险业务规则、失败恢复和权限边界，并保证测试环境与生产依赖行为足够接近。

### 15.4 如何定位一次线上请求？

**口述：**“我先拿 requestId 从入口日志找到这次请求，再沿着业务记录查对应任务、队列 job 和 Worker 日志。异步流程不一定能只靠一个字段串到底，所以需要用任务 ID 和业务 ID 继续关联。日志里的密钥和 Token 要脱敏。”

**技术细节：** 服务端为请求生成或透传 `requestId`，响应和日志携带这个 ID；AI 用量、额度与审计记录可保存关联的 requestId。Outbox 表本身没有独立的 requestId 字段，它保存业务聚合 ID 和任务 ID；排查异步任务时要从业务记录关联到 Outbox、BullMQ jobId 和 Worker 日志。敏感凭据和上游错误中的密钥会在日志前脱敏。

**通用版答案：** 可观测性至少要有结构化日志、请求链路 ID、关键业务审计和健康指标。日志要能定位问题，同时避免记录 Token、密码和第三方密钥；错误信息给用户可读内容，内部日志保留足够上下文。

### 15.5 Docker Compose、Nginx 和 Worker 如何部署？

**口述：**“生产用 Compose 启动 Nginx、前后端、数据库、Redis 和 Worker。发布时先备份、做数据库迁移，再确认 server ready，最后验证登录、上传和 AI 流式链路。SSE 经 Nginx 代理时要关闭缓冲，否则用户看不到实时输出。”

**技术细节：** 生产由 Compose 编排 Nginx、静态前端、Nest server、server-worker、PostgreSQL 和 Redis。Nginx 负责 HTTPS、静态资源、API 反向代理和 SSE 的 `proxy_buffering off`；数据库迁移先执行并确认 server ready，再启动 Worker 和最终流量。发布前后检查 health、Cookie、上传和 AI SSE，失败时按上一可用提交回滚并保留日志。

**通用版答案：** 部署设计要说明进程职责、启动顺序、配置注入、健康检查、迁移策略和回滚方式。反向代理还要关注超时、缓存、压缩和流式响应缓冲，不能只验证首页能打开。

### 15.6 Cookie、CORS 和反向代理为什么容易出问题？

**口述：**“这类问题我先看浏览器实际有没有带 Cookie，再看 Origin、SameSite、Secure 和代理转发的头。开发环境是多个 Origin，生产通过 Nginx 统一入口，配置不一致就容易出现‘登录成功却无法续期’。”

**技术细节：** 本地用户端、管理端和 API 可能是不同 Origin，生产则通过 Nginx 统一到同源路径。开发代理可能改写浏览器的 Origin；服务端先校验允许的 Origin，在开发代理场景可回落检查允许的 Referer。Refresh Cookie 的 `HttpOnly`、`Secure`、`SameSite` 要与部署方式匹配，CORS 也只允许可信来源。排查“登录成功却无法续期”时，应看浏览器实际发送的 Cookie、Origin 和 Referer，以及代理转发后的请求头。

**通用版答案：** CORS 是浏览器跨源访问规则，Cookie 是否发送还受 `SameSite`、`Secure`、域名和请求凭据配置共同影响。应从浏览器实际 Request/Response Headers 排查，不要直接把白名单放宽到所有来源。

### 15.7 Mock 数据和真实后端如何平滑切换？

**口述：**“我让 Mock 和真实接口走同一套 service 契约。切换到真实后端时，页面不应该再依赖 Mock 的特殊字段；上线前会关掉 Mock，用真实登录、权限和数据库走完关键流程。”

**技术细节：** Mock 只负责前端交互开发和演示，真实接口接入后仍通过相同的 service 和数据映射层进入页面。响应解包、字段映射、错误和 loading 状态不能只在 Mock 分支处理；上线前通过环境配置关闭 Mock，并用真实 API、数据库和权限链路验证关键流程。

**通用版答案：** Mock 应尽量复用真实接口契约，避免页面依赖 Mock 特有字段。切换点放在请求适配层，页面不感知数据来源，同时要保留一条真实环境验收路径。

### 15.8 国际化和权限菜单如何共同维护？

**口述：**“菜单的权限码、路由 key 和显示文案是三件事。后端决定用户能看哪些菜单，前端用稳定 key 找页面和翻译文本；改文案不会改权限，改权限也不用改翻译。”

**技术细节：** 菜单项保存稳定的 locale ID，前端在路由和菜单渲染时做本地化；权限字段决定菜单和页面是否可见，后端仍负责最终鉴权。这样文案变化不需要修改权限码，权限变化也不会污染翻译文件。公开区和工作区的多语言范围按当前实现分别控制，不能把规划中的全站国际化说成已经完成。

**通用版答案：** 权限标识、路由标识和展示文案应分离。国际化使用稳定 key，权限使用稳定 code，前端负责体验，后端负责安全边界。

### 15.9 性能指标如何避免变成“拍脑袋优化”？

**口述：**“我先明确要改善哪项指标，再用同一口径对比。比如首屏看资源体积和 Web Vitals，AI 对话看流式体验，接口看 p95。没有可比样本时只说明做了什么优化，不编造收益。”

**技术细节：** 项目记录 Web Vitals、接口 p95、路由耗时和构建产物，用数据判断懒加载、SSE 分帧和响应式调整是否有效。PDF、图表等重依赖不放入口包，AI 增量按帧提交，接口 p95 与页面指标分开统计。优化前后要保留同一口径的样本，不能只凭主观感觉说变快了。

**通用版答案：** 先定义指标和采样口径，再定位最大成本，最后用同口径数据验证。前端关注 LCP、INP、CLS、包体积和接口耗时；后端关注 p95/p99、错误率、队列积压和数据库慢查询。

### 15.10 搜索、分页和大数据量列表怎么扩展？

**口述：**“目前的列表主要由 PostgreSQL 过滤和分页，前端只取当前页。数据增长后，我会先看查询计划和索引；如果需要复杂全文检索，再评估专门搜索引擎，而不是一开始就加一套基础设施。”

**技术细节：** 当前内容和管理列表优先使用 PostgreSQL 查询、过滤和分页，页面通过 ProTable 处理表格状态；搜索规模扩大后再评估 Meilisearch 等独立搜索引擎。接口需要限制 page size、稳定排序和必要索引，不能让管理端一次加载全部内容。前端列表继续区分 loading、empty、error 和 forbidden。

**通用版答案：** 小规模数据可以用数据库过滤和分页，数据量、全文检索和排序需求增长后再引入搜索引擎。无论采用哪种方案，都要明确分页稳定性、索引、权限过滤和查询超时。

### 15.11 PostgreSQL 索引、事务隔离和慢查询怎么回答？

**口述：**“索引要按真实的过滤和排序条件建，不能看到字段就加。慢查询我会先看 EXPLAIN ANALYZE、扫描行数和锁等待。并发一致性通常靠唯一约束、条件更新和必要的行锁，而不是直接把所有事务调到最高隔离级别。”

**技术细节：** 项目先围绕实际查询建立索引，例如用户、内容状态、可见性、任务状态和时间排序等组合条件；不会因为每个字段都可能筛选就盲目加索引。排查慢查询时先看 `EXPLAIN ANALYZE`、扫描行数、排序和锁等待，再决定调整索引、查询条件或分页方式。事务隔离优先使用 PostgreSQL 默认的 Read Committed，额度、任务终态和版本冲突通过条件更新或必要的行锁保证业务规则；只有确实需要更强一致性时才提高隔离级别。

**通用版答案：** 索引要围绕过滤、连接、排序和唯一约束设计，并用执行计划验证是否生效。事务隔离级别越高，冲突和开销通常越大，应先用唯一约束、条件更新和合理锁范围解决并发，再按业务选择隔离级别。慢查询优化要结合 SQL、数据分布和锁等待，不能只看平均耗时。

### 15.12 Redis 用了哪些数据结构，限流如何跨进程？

**口述：**“Redis 在这个项目里存会话缓存、临时计数和队列状态。多个进程共享计数，限流不会各算各的。不过当前通用计数方法的 INCR 和 EXPIRE 是两步，进程刚好在中间退出时可能漏掉过期时间，这是我已识别的边界。”

**技术细节：** Redis 在项目中承担会话缓存、登录失败和 AI 并发计数、短期停止标记以及 BullMQ 底座等职责。当前主要使用 String、计数器和 `SET ... NX EX` 抢占标记；需要按字段或成员维护的集合时再评估 Hash 或 Set。多个服务实例共享 Redis 计数，因此不会像进程内计数那样各算各的。当前通用 `incrWithTtl` 先执行 `INCR`，首次计数时再执行 `EXPIRE`，两步不是原子操作；如果进程恰好在两步之间失败，key 可能没有 TTL。面试时应说明这是已识别的边界，后续可用 Lua 脚本把计数和设过期时间合成一次原子操作。

**通用版答案：** Redis 适合低延迟、共享和有过期时间的数据。分布式限流需要原子操作、明确窗口、过期时间和失败策略，不能用单机内存计数器代替。还要考虑热点 key、内存淘汰、持久化和 Redis 故障时的业务影响。

### 15.13 SSE 断线重连、代理超时和连接数怎么处理？

**口述：**“SSE 断了不能直接重发生成请求，否则可能重复生成。当前页面卸载会中止浏览器持有的流；服务端感知连接关闭后请求停止生成。用户点停止则会显式调用停止接口。重进页面时应先查会话和消息状态，再决定展示结果还是允许重试。代理要关闭缓冲，服务端也限制单用户并发。”

**技术细节：** 文本 SSE 使用 `STARTED/DELTA/DONE/ERROR` 事件，前端按事件边界解析。`useAiChat` 在页面卸载时取消调度器并 `abort` 浏览器请求，**没有在清理函数中调用停止接口**；显式点击停止才经 `stopAiMessage` 请求服务端。Nest 监听响应 `close` 后调用 `runtime.requestStop`，并限制单用户并发。重进页面不能把重新提交消息当成断点续传，应先查询已有会话/消息状态。Nginx 对 SSE 关闭响应缓冲并配置读取超时。断线后自动恢复到哪一条增量事件，本项目没有完整的事件 ID 重放实现，不应声称已支持无缝续传。

**通用版答案：** SSE 需要处理半包、断线、重复事件、心跳、超时和连接释放。重连策略必须有事件 ID 或业务状态依据，不能无条件重放副作用请求。生产环境还要检查反向代理缓冲、超时、负载均衡粘性和单实例连接上限。

### 15.14 如何防 XSS、CSRF、SQL 注入和恶意文件？

**口述：**“我把安全检查放在真正的数据边界：接口输入校验，数据库查询用参数化方式，内容展示过滤不可信 HTML，Cookie 续期配合来源校验，上传完成后查大小、文件内容和归属。ZIP 还要防路径穿越和解压炸弹。”

**技术细节：** 服务端使用 DTO 校验、Prisma 参数化查询和权限 Guard，避免把用户输入拼接成 SQL；Markdown 和富文本展示需要经过允许列表过滤，不能把原始 HTML 直接当可信内容渲染。Refresh Token 使用 HttpOnly Cookie，同时配合 SameSite、Origin/CORS 校验和请求方法约束降低 CSRF 风险。上传完成时检查文件大小、魔数和归属，并计算、保存 SHA-256 摘要，ZIP 拒绝路径穿越并限制条目数、展开大小和压缩比；生产如接收不可信办公文件，还需要增加病毒扫描和隔离处理。

**通用版答案：** XSS 主要靠输出编码和内容清洗，CSRF 主要靠 SameSite、CSRF Token 或 Origin 校验，SQL 注入靠参数化查询和最小权限，文件安全要校验内容而不是只看扩展名。安全措施要覆盖输入、存储、处理、输出和下载的完整链路。

### 15.15 数据库迁移失败时如何发布和回滚？

**口述：**“数据库迁移失败时，先停止继续发布，保留日志和数据库现场。平时尽量做向前兼容迁移：先加新结构，再发兼容代码，最后才删旧结构。应用代码可以回滚，但已经变更的数据不能简单靠 Git 回滚。”

**技术细节：** 生产发布先备份并检查迁移脚本，再执行 `prisma migrate deploy`，确认数据库和 server readiness 后启动 Worker 与 Nginx。迁移采用向前兼容思路：先增加字段或表，再发布同时兼容新旧结构的代码，最后再清理旧字段；不可逆数据变更不能依赖简单的 Git 回滚。失败时先停止继续发布、保留日志和数据库状态，按迁移设计执行补偿脚本或恢复上一版本应用，必要时从备份恢复。

**通用版答案：** 应用回滚和数据库回滚是两个问题。可靠发布要使用向前兼容迁移、备份、健康检查和明确的补偿方案，避免直接在生产执行破坏性 `reset`。对于大表变更，还要考虑锁表时间、在线迁移和分批回填。

### 15.16 如何量化项目性能和业务效果？

**口述：**“我会把指标和实际样本一起说。项目能观察页面 Web Vitals、接口耗时和发布标记，但还没有能证明大规模业务增长的数据，所以面试时只给可复核的技术指标和验证方法。”

**技术细节：** 性能方面关注 LCP、INP、CLS、首字节时间、接口 p95/p99、入口包体积、SSE 首 token 延迟和 Worker 任务耗时；AI 还要看成功率、失败率、取消率、额度消耗和重复扣费数。优化前先固定采样范围和设备条件，优化后用同口径比较。项目当前已经有 Web Vitals、接口耗时和发布标记采集，但不能把内部开发指标包装成大规模线上业务成果。

**通用版答案：** 指标要和用户体验或业务目标关联，例如首屏可交互时间、任务成功率、错误率、留存或转化。没有真实流量时可以报告测试样本、基线和验证方法，不能编造并发量、用户数或收益。

### 15.17 面试官问“你到底负责了多少”时怎么回答？

**口述：**“PersonalHub 是我个人主导的，AI Agent 参与方案、编码和自查，是主要开发工具。我负责架构取舍和验收；前端流式渲染、后端权限和异步任务，我都能沿代码、测试和异常路径讲清楚。还没完成的能力会明确说出来。”

**技术细节：** 按模块和证据说明责任边界：用户端/管理端页面、请求封装、SSE 解析和流式渲染，以及认证、权限、内容、文件、AI、额度、任务链路，均可结合仓库回答。共享类型、测试和部署文档同样有记录。AI Agent 深度参与方案、编码和自查；我负责判断接口契约、状态机、异常处理是否正确，并完成验收。Fake Provider、Mock 与后续 Next.js/Flutter/真实媒体接入要分清已实现、开发辅助和规划。

**通用版答案：** 不要只说“整个项目都是我做的”，也不要把不会解释的模块算成自己的成果。可以按需求分析、方案设计、核心编码、联调测试和上线排障逐项说明，并准备对应代码路径、测试用例和取舍理由。

## 16. 面试时建议主推的三个项目难点

以下是口述稿，描述仓库可核实的实现；个人参与程度、线上数据和排障经历需按真实经历调整。

### 难点一：AI SSE 全链路

**约一分钟口述：**“AI 对话看上去只是把文字一段段显示出来，实际碰到了几个问题。网络每次给我的一段数据，可能只有半条 SSE 事件，所以我先把事件拼完整，再识别开始、正文和结束。正文如果每来一点就更新 React，页面容易频繁渲染，我就把它按帧提交。还有一个容易漏的顺序问题：结束事件到了，不代表前面的文字已经画出来，所以我让结束状态排在文字后面。用户切换会话时，原来的生成仍写回原会话；点停止时也先保留已经收到的内容。这套处理比直接在组件里 setState 多一点状态管理，但这些边界能放在一处解决。”

**如何证明：** 查看 `aiSse.ts`、`aiStreamScheduler.ts`、`useAiChat.ts`；测试中包含切换会话旧流继续生成、STARTED 前停止、过期历史不能覆盖新消息的场景。可手动发送后切换会话，再返回检查归属，点击停止确认文本保留。这里有代码和用例证据，不虚构帧率提升百分比。

### 难点二：幂等、额度和异步任务一致性

**约一分钟口述：**“做 AI 生成时，我比较担心用户重复点击或网络超时后重试，最后生成两次、扣两次额度。这个问题我分三层处理。请求层用幂等键识别同一请求；任务创建时，业务记录和待发送事件一起写入数据库，队列暂时失败还可以补投；额度层先预占，结束时只允许尚未结算的记录完成一次结算。因为队列可能重复投递，Worker 也会先看任务状态。这样即使前端没拦住重复点击，后端仍有自己的保护。外部模型厂商是否重复收费，还需要供应商幂等能力或对账配合。”

**继续追问：** 同键后来者最多等待约 10 秒，仍未完成返回 409；运行中声明会刷新心跳。数据库幂等不能自动约束第三方调用是否重复收费，这是外部幂等与对账的范围。

**如何证明：** 对照 `idempotency.interceptor.ts`、`ai-quota.service.ts`、`outbox.dispatcher.ts` 及对应测试；验证同键同体回放、换体冲突、重复结算余额只变一次。没有实测线上吞吐时，只讲规则与用例。

### 难点三：认证、RBAC 和私密内容授权

**约一分钟口述：**“权限这块我没有只做菜单隐藏。我先区分用户是谁、能做什么、能看哪条数据。前端根据权限调整菜单和按钮，后端收到请求后还会检查当前会话、操作权限和内容归属。私密内容尤其容易漏入口：详情页拦住了，但列表、章节或者 AI 引用又把内容带出来，所以这些入口都复用访问规则。还有两个管理员同时改授权名单和公开状态的情况，我让它们在数据库里按同一条内容记录排队处理，避免出现前后不一致。”

**如何证明：** 查看认证服务、PermissionsGuard 和 content-visibility，以及认证与内容 HTTP 测试。准备作者、指定读者、未授权读者三个账号，分别验证列表、详情和 AI 引用。跨 Origin 恢复与 Cookie 配置可以演示，但不要称整个认证系统无状态。

## 17. 一段可以直接背的项目介绍

“PersonalHub 是我个人主导的知识中台和 AI 工具箱。前端分用户端和管理端：用户端有内容阅读、工作区和 AI 对话，管理端负责用户、权限和内容运营。后端用 NestJS，核心数据在 PostgreSQL，Redis 放临时状态，BullMQ 处理耗时任务。AI Agent 是我的主要开发工具，参与前后端方案、编码和自查；我负责架构取舍与验收。

这里最值得展开的是三件事：AI 对话要正确处理流式事件和切换会话；生成任务要防重复请求和重复扣费；私密内容要在所有入口都守住权限。三件事都有对应实现和测试，我可以结合其中一块具体讲遇到的问题和取舍。

目前 React 用户端、管理端和 Nest 主链路已经落地。Next.js、Flutter 和部分真实媒体厂商接入还在后续计划里，我不会把它们算作已交付的功能。”
