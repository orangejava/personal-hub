# 小册 ZIP 编码与大文件上传

## 场景背景

跨平台 ZIP 的文件名可能没有 UTF-8 标记。部分 Windows 压缩工具会把中文名和正文保存为 GBK 字节，解析器若默认按 CP437 或 UTF-8 读取，就会在目录和章节标题里出现乱码。大文件上传还需要处理短期预签名 URL 到期及 COS Multipart 的分片限制。

## 核心机制

- ZIP 文件名优先按 UTF-8 标记或 Unicode Path 扩展字段处理；缺少标志时先严格尝试 UTF-8，再回退 GB18030，兼容漏写 UTF-8 标志的压缩工具。
- 文件正文先严格尝试 UTF-8，再回退 GB18030。路径安全校验要在解码后执行。
- COS 每个分片签名 URL 有期限；上传会话与签名 URL 的生命周期应分开管理，重试前刷新签名。
- 为避免一次生成数千个 URL，按批次请求分片签名，浏览器再以有限并发上传。
- 管理员配置的是业务上限；对象存储的单片/分片数上限和解压安全上限是独立的技术边界。

## 本项目调用链

后台 `file.policies` 保存 `TEMPORARY_IMPORT` 与 `BOOKLET_SOURCE` 的 `maxBytes`；工作区创建会话前读取策略。上传超过单 PUT 阈值后，服务端计算分片尺寸，前端分批取签名并上传。导入 Worker 解析 ZIP，解码章节文件名与正文后生成章节索引。

## 常见错误

- 看到 COS 403 就先怀疑 CORS。检查 XML 错误码；`Request has expired` 通常是签名 URL 超时，CORS 只决定浏览器能否跨域读取响应。
- 只修浏览器目录展示，但解析器仍把错误标题持久化。应在 ZIP 解析入口修复编码，已有乱码导入记录需要重新导入。
- 上传上限升高后忘记调整数据库整数类型；`file_assets.size` 使用 BIGINT，API 仍以安全整数 JSON number 表示。
- 上传配置不设业务最小/最大值，但 COS 单片最大 5 GB、最多 10,000 片是协议边界。解压总量阈值为 `max(500 MiB, 后台配置 × 100)`；实际 ZIP 仍受 100 倍压缩比、章节数量、单章体积、文件名等元数据累计 8 MiB 与 Markdown 正文累计 64 MiB 限制。元数据上限必须在缓存全部 ZIP 条目前逐项检查，否则长文件名可以绕过正文上限耗尽 worker 内存。
- 续签接口只接受未过期且仍处于 `UPLOADING` 的会话；失败或过期会话要求重新上传，避免延长无效对象存储分片。

## 手动验证

1. 用后台配置把 ZIP 上限调整到大于 50 MiB，保存后刷新页面确认数值保留。
2. 导入一个章节名称含中文的旧编码 ZIP，检查阅读器目录与章节标题。
3. 上传大于单 PUT 阈值的 ZIP；暂停超过 15 分钟后继续或重试，确认分片 URL 被重新签发。
