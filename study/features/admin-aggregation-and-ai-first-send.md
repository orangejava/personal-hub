# 后台聚合统计与 AI 首次发送

## 场景

运营数字从 mock 切到真实接口时，先为每个数字定义来源、过滤条件和时间边界。流式对话首次发送往往先创建会话，因而“点击发送”不等于“消息已被接收”。

## 实现顺序

1. 从页面 service 追到 Nest Controller，确认路径、权限与 Umi 全局解包后的业务对象类型。
2. 统计按数据库字段定义：未删除内容、全部用户、上海自然日内跨内容去重的读者标识、本周首次发布时间。去重放在数据库执行，按查询条件建立日期索引。
3. 首次发送等待会话创建；等待中禁重。只有用户气泡写入状态后才清除本次草稿。创建失败由页面提示，流式失败由助手气泡提示。
4. 对上海周一零点、创建失败重试和重复点击写定向测试。
5. 多会话 SSE 以会话 ID 作为状态键；切换只更新当前选中 ID，流的增量、终态和停止操作都按原 ID 处理。首次建会话的等待也占用并发名额，避免三个流之外再悬挂创建请求。

## 常见错误

- `Date#setHours(0)` 使用服务器本地时区；数据库 `DATE` 与页面“今日”口径可能错一天。上海自然日应显式换算。
- 将 `timestamp` 转 `date` 也可能依赖数据库会话时区；查询 PostgreSQL `DATE` 时传明确的 `YYYY-MM-DD`。
- 页面在异步建会话之前清空输入，会把失败伪装成无响应。
- 用单份 AbortController 管理所有会话时，切换视图会误停旧流；晚到的首屏会话列表也可能覆盖刚建的会话。
- 用 `COUNT(*)` 统计浏览记录是阅读次数，用 `COUNT(DISTINCT subject_hash)` 才是此业务定义下的近似读者数。

## 手动验证

手机宽度打开 AI 对话，首次建会话完成后应看到问题进入对话区；断开建会话请求时应显示错误、保留草稿，恢复后可重试。让 A、B、C 三条会话同时生成，切换回来分别核对回复；第四条应提示上限并保留草稿。后台用有 `dashboard:read` ALL 权限的账号打开运营概览，核对四项数字，并在服务端失败时检查重试态。

## 并发和异步回写的排障方法

先把流程画成“创建 → 本地占位 → STARTED 换真实 ID → 增量 → 终态落库 → 释放名额 → 刷新历史”。每个等待点都检查：用户此时切换、离页、停止或删除，后续回调应该写到哪里。

仅检查“现在是否生成中”不能挡住旧响应：一次请求可能跨过完整的一次生成。因此历史请求应携带本地会话版本，返回时版本不同就丢弃。未入库失败消息属于本地状态，需要按 ID 合并保留，不能直接用历史数组替换。

取消 fetch 只证明客户端不再读取；服务端仍可能计费。显式 stop 要等待服务端终态，而断连需要服务端监听响应 close 并取消厂商调用。正常停止导致的 AbortError 应与厂商故障分开处理，前者保存部分文本并按实际输出结算。

“先隐藏旧回答，再检查额度”会让失败重试丢失可见数据。正确顺序是先校验和预占，再在同一事务内创建新变体、隐藏旧变体、设置生成指针。用带 token 的锁让删除和发送互斥，释放前验证持有者，防止过期请求删掉新锁。
