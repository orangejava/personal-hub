# AI Provider 密钥请求与落库

## 场景

后台保存 API Key 时，即便响应不回显，浏览器 Network 的请求数据仍可看到明文。HTTPS 保护链路，但开发者工具仍展示提交前的 JSON。需要让请求 JSON 只包含密文，同时避免数据库保存明文。

## 两层数据流

1. 管理端 `GET /api/v1/admin/ai/credential-key` 读取服务端 P-256 公钥。该接口只给有 `ai:provider:manage` 权限的管理员。
2. 浏览器为每次保存生成临时 P-256 密钥，与服务端公钥做 ECDH；HKDF-SHA256 派生 AES-256-GCM 密钥，加密输入框中的 Key。请求体仅发送 `keyId`、临时公钥、salt、iv、ciphertext。
3. Nest 校验密文信封，按服务端私钥解密。私钥由环境变量主密钥做独立用途的 HKDF 派生。格式错误、版本错误和认证失败统一返回 `AI_CREDENTIAL_INVALID`，不暴露密钥细节。
4. `AiCredentialService` 再用主密钥 AES-256-GCM 加密明文并写 `ai_provider_credentials`。Provider 响应只返回 `hasKey`，不会返回密文、掩码或明文。

请求加密和落库加密分工不同：前者避免请求 JSON 明文，后者保护数据库。生产仍需 HTTPS；页面输入框、浏览器内存及服务端本次处理内存中仍短暂存在明文。当前未实现多版本主密钥自动解密：轮换前必须迁移已有凭据，旧页面也需要重新获取公钥。

## 关键文件

- `apps/admin-web/src/services/admin/aiCredentialTransport.ts`：浏览器 WebCrypto 加密。
- `apps/server/src/modules/ai/ai-credential.transport.ts`：私钥派生与请求解密。
- `apps/server/src/modules/ai/ai-credential.service.ts`：落库加密、读取及环境变量回退。
- `apps/server/src/modules/ai/ai.service.ts`：Provider 目录与凭据同事务保存。
- `packages/shared-types/src/admin.ts`：公钥和密文信封契约。

## 验证与常见错误

用一个专门测试用的 Key 保存，检查 Network 的 POST/PATCH Request Payload 与 Response 搜不到该值，刷新后仅显示「已配置」。直接提交旧 `apiKey` 字段应返回 400。关闭网络请求加密而只加密数据库，无法满足 Request Payload 检查；把公私钥都写在前端也不能提供保护。不要在日志、审计详情、幂等响应和测试失败输出中打印 Key。

## 配置写入的事务边界

同一厂商的系统凭据由部分唯一索引约束。并发首次保存时，不能在 PostgreSQL 事务里捕获唯一冲突后继续 UPDATE：事务已经失败。这里使用参数化 `INSERT ... ON CONFLICT ... DO UPDATE`，让数据库原子处理冲突；目录和凭据仍在同一事务内。

模型目录与角色授权是两条不同权限链。新增模型只写目录，角色白名单通过独立权益接口编辑；空数组在本项目代表“不限制”，不能拿空数组表达“禁止所有模型”。默认模型以工具行的外键为准，CHAT 和 TEXT 分别指向自己的模型，单一 `isDefault` 仅作为兼容摘要。配置写入共用事务锁，避免两个管理员同时更新默认关系。

PATCH 先把请求与旧记录合并，再校验最终价格、启用状态和工具范围；否则“旧记录有价格，清空后仍允许启用”的错误会延迟到发送消息才出现。首次对话还没有 sessionId，前端需要用临时设置槽保留模型选择，创建会话时一起传给服务端。

## 本轮回归路径

新增流程现在分为“保存目录 → 配置访问权限”。保存后自动进入「模型访问权限」；已有模型从模型列表的「配置访问权限」进入。点击指定角色的「授权模型」会保留原有选择并预选当前模型，直到点保存才提交。只看“已启用 / 用户可见 / 默认”不能判断用户一定可用，还需要检查列表的“已授权角色”。授权统一按角色维护，模型页只是同一流程的快捷入口，避免两套规则不一致。这次修复只补齐配置流程，不直接修改现有角色数据。

1. 管理端「AI 配置 → 模型管理」新增一个支持 Chat 的模型，配置整数消耗并启用、对用户可见。到「模型访问权限」为受限制的测试角色勾选该模型，保存。以该角色刷新用户端 Chat，确认下拉可见；未授权角色仍不可见。已有“全部模型”角色会自动可见，测试隔离时应使用显式白名单角色。
2. 分别设置 Chat 和 Text 的默认模型，重新打开编辑框和对应用户页面，确认彼此不覆盖。清空固定消耗但保留输入/输出消耗，应能保存；启用状态下全部为零且固定消耗为空，应提示失败。暂停唯一可用模型后，用户端显示无可用模型并禁止发送。
3. 用无对话历史的测试账号打开 Chat，在发送前改选另一个可用模型，确认选择保留；展开高级设置修改上下文，再创建会话，确认设置随会话保存。真实厂商消息会产生实际调用费用，可先用 Fake 模型检查交互；缺失密钥的失败、额度释放和不伪造回复已由隔离 HTTP 测试覆盖。

对应代码：`ai-model-config.ts` 维护最终配置校验与默认关系；`ModelEntitlements.tsx` 管理角色授权；`useAiAvailableModels.ts` 选择当前工具默认模型；Chat 页面保存未创建会话时的设置。HTTP 测试用独立 PostgreSQL/Redis 容器，避免修改开发账号、凭据和额度。
