# 系统设计思考清单

> 用于回答一个问题：如果让我从 0 重新设计一个系统，我应该先考虑哪些方面，而不是一上来就选框架或开写代码。

---

## 1. 先想清楚“这个系统为什么存在”

在技术之前，先确认业务问题：

1. 这个系统服务谁？
2. 这些用户最核心的任务是什么？
3. 系统的成功标准是什么？
4. 哪些功能是 MVP，哪些是后续版本？

### 以本项目为例

- 服务对象：自己 + 未来少量访客 + 管理员角色
- 核心任务：
  - 看内容
  - 管内容
  - 用 AI 工具
  - 管模型、权限、站点配置

如果这一步不清楚，后面很容易陷入“技术很先进，但功能不聚焦”。

---

## 2. 用户与角色

要设计任何系统，第二步都要问：

- 系统里有哪些角色？
- 各角色分别能看到什么、操作什么？
- 有没有“同一资源，不同角色权限不同”的情况？

### 常见角色模型

- 访客
- 注册用户
- 内容编辑者
- 管理员

### 本项目里的实际影响

- 决定哪些页面公开访问，哪些必须登录。
- 决定 API 是否需要鉴权。
- 决定后台菜单显隐与按钮权限。

---

## 3. 核心对象与数据模型

写系统前先找核心对象，也就是数据库里的主要实体：

- 用户 `User`
- 角色 `Role`
- 权限 `Permission`
- 内容 `Content`
- 分类 `Category`
- 标签 `Tag`
- AI 会话 `AiSession`
- AI 消息 `AiMessage`

### 要问的关键问题

1. 每个对象有哪些关键字段？
2. 它们之间是一对一、一对多还是多对多？
3. 哪些字段需要唯一约束？
4. 哪些字段需要索引？
5. 哪些是“状态字段”？

### 常见错误

- 一开始不建状态字段，后面只能靠很多布尔值补丁式叠加。
- 不提前想好唯一约束，后期很容易出现脏数据。

---

## 4. 关键业务流程

系统设计不是只看表结构，还要看“流程”是否闭环。

### 每个核心功能都要问

1. 入口是什么？
2. 用户操作顺序是什么？
3. 依赖哪些前置条件？
4. 失败时怎么处理？
5. 结果如何反馈给用户？

### 本项目的关键流程示例

- 注册 → 登录 → 获取 Token → 进入工作区
- 内容创建 → 保存草稿 → 发布 → 触发 revalidate → 前台可见
- 发起 AI 对话 → SSE 流式返回 → 保存消息 → 记录 Token 消耗

---

## 5. 前端信息架构

前端不是“把接口堆到页面上”，而是先决定信息结构：

- 页面怎么分组？
- 一级导航是什么？
- 哪些页面是公开的，哪些属于工作区？
- 哪些交互适合服务端渲染，哪些适合客户端交互？

### 要考虑的维度

- 页面层级
- 导航结构
- 关键操作路径
- 组件复用边界
- 状态放在哪一层

---

## 6. API 设计

设计 API 时，不只是“能调通”，还要考虑长期维护：

- 路径是否语义清晰
- 方法是否符合 REST 习惯
- 分页是否统一
- 错误码是否统一
- 鉴权方式是否一致
- 是否便于后续接 Flutter / 第三方客户端

### 本项目已明确的约定

- RESTful 风格为主
- 列表统一 Offset 分页
- JWT AccessToken + RefreshToken
- 错误格式统一返回 `code/message/timestamp`

---

## 7. 非功能性需求

很多系统不是死在功能，而是死在非功能性需求没想清楚。

必须考虑：

- 性能：访问量大时是否扛得住
- 安全：鉴权、权限、XSS、CSRF、SQL 注入
- 可维护性：模块边界是否清楚
- 可扩展性：后面新增 AI 模型、接 Flutter 容易吗
- 可观测性：出错后能不能定位
- 成本：服务器、对象存储、模型调用成本

### 本项目具体表现

- AI 接口要限流，不然容易被滥用。
- 内容页要 ISR，不然全部 SSR 成本高。
- 后端代理 AI Key，不能前端直连模型厂商。

---

## 8. 部署与运维

系统设计不能只看“本地能跑”，还要考虑上线：

- 怎么构建？
- 怎么部署？
- 怎么回滚？
- 怎么做环境隔离？
- 怎么备份数据库？
- 怎么监控运行状态？

### 本项目的部署抽象

- Web：Next.js 容器
- API：NestJS 容器
- DB：PostgreSQL
- Cache：Redis
- Reverse Proxy：Nginx

---

## 9. 技术选型方法

重新设计系统时，不要先问“什么最火”，而要按下面顺序问：

1. 业务需要什么能力？
2. 团队最熟什么？
3. 这个技术是否能支撑未来 1 到 2 年的扩展？
4. 学习成本是否值得？
5. 社区和生态是否成熟？

### 一个实用判断标准

如果一个技术只是“看起来高级”，但不能明显提升以下任一项，就要谨慎：

- 开发效率
- 维护性
- 性能
- 安全性
- 扩展性

---

## 10. 一个通用的系统设计顺序

以后设计任何系统，都可以按这个顺序走：

1. 业务目标
2. 用户角色
3. 核心对象
4. 核心流程
5. 前端信息架构
6. API 设计
7. 数据模型
8. 权限模型
9. 非功能性需求
10. 部署与运维
11. 技术选型
12. 开发排期

---

## 11. 面向本项目的系统设计检查表

开始写代码前，至少确认下列问题都有答案：

- 首页和内容页哪些需要 SEO？
- 内容发布后如何刷新缓存？
- 登录态怎么存？
- 权限是前端控制还是后端控制，还是两者都要？
- 数据库哪些字段需要唯一约束和索引？
- AI 调用失败时前端如何提示？
- 文件上传的上限、存储位置、访问方式是什么？
- 后台哪些功能一定要首版上线？
- 本地、测试、生产三套环境怎么区分？
- 线上出问题后看哪里排查？

---

## 12. 你之后自己设计系统时要刻意训练的能力

1. 能把模糊需求拆成清晰模块。
2. 能区分“现在必须做”和“以后再做”。
3. 能从用户路径反推页面与接口，而不是只从技术出发。
4. 能提前想到权限、缓存、部署、监控等非功能性问题。
5. 能解释为什么选这个方案，而不是只会照着模板搭。

> 系统设计的本质不是“会画图”，而是“能把复杂问题拆成清楚、可落地、可验证的结构”。
