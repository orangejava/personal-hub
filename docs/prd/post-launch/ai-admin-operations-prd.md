# AI 后台运营 PRD

> 状态：下一步开发计划
> 最后更新：2026-09-23
> Worktree：AI 后台
> 计划评分：9 / 10
> 关系：扩展 [../long-term/ai-tools-prd.md](../long-term/ai-tools-prd.md) 的上线后运营能力；实现时需要同步 Canonical API、数据模型和 `apps/server/docs/implementation/ai/`。

## 1. 目标

首版 AI 已能使用 Fake / OpenAI-compatible Provider。下一步要把 AI 从「能用」升级为「可配置、可运营、可控成本、可审计」。

本 PRD 覆盖：

- AI Provider 和模型配置中心
- 用户自备 API Key 能力与总开关
- AI 用量统计
- 用户额度调整
- AI 消耗倍率
- 公共额度发放能力
- 每日登录奖励
- 连续签到日历

## 2. 不做

- 用户充值、支付、订单、发票
- 自研模型、模型训练、模型微调
- 自研模型备案流程
- LoRA / ComfyUI
- 复杂活动运营平台

说明：当前没有自研模型，因此不存在自研模型备案这条功能路径。只记录系统和用户调用的外部 Provider。

## 3. 阶段 A：AI 配置中心

### 3.1 管理员 Provider

后台支持管理员配置系统 Provider：

- Provider 名称
- Provider 类型，如 OpenAI-compatible
- Base URL
- API Key
- 是否启用
- 备注
- 是否已备案模型来源
- 备案说明或备案号字段

API Key 必须只写不回显。后台只能看到「已配置 / 未配置」状态，不显示明文。

### 3.2 模型管理

每个 Provider 下可以维护模型：

- 模型 ID
- 展示名称
- 能力类型：chat / text / image / video
- 上下文长度或参数限制
- 是否启用
- 默认倍率
- 是否推荐
- 排序

用户端只展示启用、当前用户有权限、当前工具支持的模型。

### 3.3 连接测试

后台提供连接测试：

- Provider 级测试：验证 Key 和 Base URL 可用
- 模型级测试：验证指定模型可调用
- 失败时展示后端 `error.message`
- 测试请求不得记录明文 API Key

### 3.4 验收

- 管理员能新增、编辑、禁用 Provider。
- API Key 保存后不可回显。
- 禁用模型后，用户端不再可选。
- 没有可用模型时，用户端展示清晰空状态。
- 连接测试成功 / 失败都有明确结果。

## 4. 阶段 B：用户自备 API Key

用户自备 API Key 保留，但必须受后台开关控制。

### 4.1 后台开关

后台可配置：

- 是否允许用户自备 Provider
- 允许的 Provider 类型
- 是否允许用户覆盖系统默认模型
- 是否允许用户自备 Key 参与额度统计

第一版默认可以关闭入口，但数据模型和接口预留。

### 4.2 用户侧能力

后续用户可在个人设置或 AI 设置中维护自己的 Key：

- Provider 类型
- Base URL
- API Key
- 启用状态
- 连接测试

用户自备 Key 同样只写不回显。

### 4.3 验收

- 后台关闭开关后，用户侧入口不可见。
- 用户自备 Key 不影响系统 Provider。
- 用户自备调用仍保留用量记录。

## 5. 阶段 C：AI 用量、额度和倍率

### 5.1 用量统计

后台需要看到：

- 全站总用量
- 按用户统计
- 按模型统计
- 按工具统计
- 按时间范围统计
- 输入、输出、图片、视频任务等维度

### 5.2 用户额度

超级管理员可以查看和调整用户额度：

- 当前可用额度
- 已预占额度
- 历史消耗
- 手动增加额度
- 手动扣减额度
- 调整原因

所有额度变化必须进入账本，不允许只改余额。

### 5.3 消耗倍率

支持按模型配置平台额度消耗倍率：

- 文本输入倍率
- 文本输出倍率
- 图片生成固定倍率或按张数倍率
- 视频生成固定倍率或按时长倍率

倍率变更只影响后续消耗，不回改历史账本。

### 5.4 验收

- 管理员能看到全站、用户、模型维度用量。
- 手动调整额度后用户余额立即变化。
- 账本可以追溯操作者、原因、变化前后值。
- 倍率变更后，新请求按新倍率消耗，旧记录保持不变。

## 6. 阶段 D：公共额度发放能力

增加 AI 额度不能写死在登录接口里。需要抽成公共发放能力，后续用于登录、签到、活动、邀请和管理员赠送。

### 6.1 发放规则

后台可配置：

- 规则名称
- 规则类型：每日登录、签到、活动、管理员赠送
- 发放额度
- 生效时间
- 失效时间
- 每用户周期内最多领取次数
- 是否启用
- 展示文案

### 6.2 默认规则

第一版内置默认规则：

- 每日首次登录发放 AI 额度
- 每个用户每天最多一次
- 默认额度由后台可配置
- 重复登录、刷新 Token、自动续期不重复发放

### 6.3 幂等

每次发放必须有幂等键，例如：

```text
daily-login:<userId>:<yyyy-mm-dd>
```

重复触发时直接返回已领取结果。

### 6.4 验收

- 用户每天首次登录获得额度。
- 同一天多次登录只获得一次。
- 关闭规则后不再发放。
- 发放记录进入额度账本。
- 登录失败和 refresh 不触发发放。

## 7. 阶段 E：连续签到日历

连续签到是公共发放能力的第一个前台化入口。

### 7.1 用户侧

用户可以看到：

- 今日是否已签到
- 连续签到天数
- 本周期奖励日历
- 今日可领取额度
- 断签提示

### 7.2 后台配置

后台可配置：

- 每日基础奖励
- 连续第 N 天额外奖励
- 是否断签重置
- 最大连续天数
- 是否循环
- 活动开始 / 结束时间

### 7.3 验收

- 用户可主动签到领取额度。
- 每天只能签到一次。
- 连续天数计算正确。
- 断签策略符合后台配置。
- 签到奖励和每日登录奖励不能重复发放同一规则额度。

## 8. 影响范围

### 后端

- API Key 加密与脱敏
- 连接测试
- 用量聚合
- 额度账本
- 额度调整
- 发放规则
- 签到记录

### 数据模型

- `ai_providers`
- `ai_models`
- `ai_user_provider_keys`
- `ai_quota_rules`
- `ai_quota_grants`
- `ai_checkins`
- `ai_usage_daily`
- `ai_quota_transactions`

实际命名以 Prisma schema 和已有模型为准。

### 前端

- `apps/admin-web`：AI 配置、用量、额度、发放规则、签到规则
- `apps/user-web`：模型选择、额度展示、签到入口、用户自备 Key 入口
- `packages/api-client`：接口方法与类型
- `packages/shared-types`：共享枚举和 DTO 类型

## 9. 风险与控制

- API Key 泄露风险：只写不回显、日志脱敏、传输走 HTTPS。
- 重复发放风险：所有发放规则必须有幂等键。
- 账本错账风险：余额只能由账本事务计算或在同一事务内更新。
- 用户自备 Key 合规风险：后台总开关默认可关闭。
- 范围过大风险：严格按 A → B → C → D → E 阶段开发和验收。
